## 확인한 조건

- 에이블리는 Android에서 `m.a-bly.com`에서 `mobile.a-bly.com`으로 이동했다. 같은 `/goods/<id>`인 경우에만 기존 배포 규칙으로 읽고, 서버에 보내는 URL은 기존 `m.a-bly.com` 상품 주소를 유지한다. 네이티브가 이동 완료를 받기 전에 도착한 메타데이터는 페이지에서 짧게 다시 전달한다. 이때 쇼핑몰에 HTTP 요청을 다시 보내지는 않는다.
- 실제 지그재그 HTML은 `og:type=website`지만 상품 JSON-LD, KRW 가격, 여러 `og:image`를 포함했다. 상품 근거 없이 제목과 CDN 이미지만 있으면 상품으로 보지 않고, 명시적인 외화 가격과 허용되지 않은 이미지는 건너뛴다.
- 이전 실행에서는 Android 무신사 `7493901`의 메인 WebView가 `403`을 반환했고, `7561001`은 시간 초과된 실행도 있었다. 이번 별도 일반 HTTP 요청에서도 무신사 및 에이블리 샘플은 `403`이었다. 별도 HTTP 응답을 앱 WebView 응답이나 앱 성공률로 해석하지 않는다. 보안 확인은 우회하지 않는다.
- 이전 검증에서 독립 웹은 쇼핑몰이나 추출 규칙을 호출하지 않았고, Android 미지원 링크도 규칙 조회 없이 수동 전환했다.

- 최종 회귀에서는 무신사 단축 링크 2·에이블리 상품 단축 링크·지그재그 제휴 단축 링크 1을 각 플랫폼에서 다시 실행해 6/6 자동 입력됐다. 앞선 무신사 간헐 실패는 이 결과로 해결됐다고 볼 수 없다.

## 메타 태그가 없는 상세 페이지 대응

Android에서 무신사 `4804589`의 상품 페이지에 도착했지만 OG 제목·상품 JSON-LD가 없어 자동 입력하지 못한 실행을 재현했다. 페이지에는 `__NEXT_DATA__`의 `Detail` 쿼리와 상품 메타데이터가 있었다. 이제 주소·쿼리·상세 상품 ID와 상품명이 맞는 경우에만 해당 데이터를 보조 출처로 사용한다. 원화 가격과 서버가 허용한 대표 이미지만 채운다.

지그재그는 `getPdpBaseInfo`의 상품 ID가 주소와 일치할 때만 같은 방식으로 보완한다. 실제 HTML 3건(`171190375`, `169420901`, `171067691`)에서 메타 태그와 JSON-LD를 제외하고 내부 데이터만 추출한 결과, 공개 메타데이터의 상품명·가격·대표 이미지 경로가 3/3 일치했다. 이는 저장된 실제 HTML을 이용한 폴백 단독 검증이다.

로컬 QA 규칙에서 가격·이미지 셀렉터를 비우고 Android WebView로 실제 상품 페이지를 열어 폴백을 별도로 검증했다. 무신사 `4804589`(24,490원), `6623590`(239,200원), 지그재그 `169420901`(35,690원) 모두 이름·가격·대표 이미지가 자동 입력됐다(3/3). 무신사 폴백 이름은 공개 상세 데이터의 상품명이며 OG 제목에 붙는 브랜드 등의 문구는 없을 수 있다.

정상 규칙으로, 무신사 3개 링크(단축 1개·직접 2개)를 Android에서 각각 3회 실행한 실제 WebView 검증은 변경 전 8/9, 변경 후 9/9였다. 소규모 비통제 반복이며 변경 후 모든 성공이 폴백을 사용했다는 뜻은 아니다. iOS 에이블리·지그재그 단축 링크도 자동 입력됐다. iOS 무신사 단축 링크는 첫 자동화에서 입력 포커스 실패로 제출되지 않았고 재실행에서는 자동 입력됐다.

## 에이블리 앱 주소와 상품 ID 확인

에이블리 `13519743`의 실제 HTML에는 앱 링크 `https://a-bly.com/app/goods/13519743`와 모바일 웹 주소가 각각 별도의 Open Graph 블록으로 있었다. 앱 주소도 같은 ID의 공식 `/goods/13519743`으로 정규화해 자동 입력한다. 두 블록에서 URL의 상품 ID와 다른 제목·이미지는 건너뛰고, `product:retailer_item_id`가 요청과 다르면 가격을 포함해 자동 입력하지 않는다. 단축·직접 주소 모두 기존 CDN 허용 목록을 유지한다.

관측한 에이블리 페이지에서는 OG·가격 메타 태그 이외에 같은 상품을 검증할 `__NEXT_DATA__`나 상품 JSON-LD를 찾지 못했다. 무신사·지그재그처럼 내부 데이터를 읽는 폴백을 추가하지 않았다. 변경 전 Android 에이블리 3회 중 1회는 자동 입력되지 않았다.

변경 후 에이블리 앱 주소·단축 주소·직접 주소와 지그재그·무신사 단축 주소를 Android와 iOS에서 각 1회씩 검증해 총 10/10에서 이름·가격·이미지가 맞았다. Android는 이름과 가격을 자동 검사하고 대표 이미지를 캡처로 비교했다. iOS는 화면에서 값이 보여도 `agent-device`의 텍스트 단언이 실패해 캡처로 대조했다. URL 확인 로그에서 새 앱 주소가 `/goods/13519743`으로 저장 후보가 된 것도 확인했다.

## 규칙 API 일시 장애

앱 재시작 시에도 서버에서 내려받고 스키마 검증을 통과한 규칙을 재사용한다. `200` 또는 ETag가 확인된 `304` 이후 5분 이내로 제한하며, `401`/`403`이나 잘못된 규칙 응답 뒤에는 이전 규칙으로 추출하지 않는다. URL 확인·보드·저장 API는 별개이며, 이 변경으로 해당 API 장애나 쇼핑몰 접근 거부가 해결되지는 않는다.

두 플랫폼에서 먼저 규칙 조회 `200`을 받은 다음, 로컬 fixture의 규칙 API만 `503`으로 전환하고 매 시도 앱을 재시작했다. 실제 쇼핑몰은 정상 경로로 요청했다. Android·iOS에서 에이블리 앱 주소 `13519743`(26,800원), 무신사 OneLink `4804589`(24,490원), 지그재그 제휴 주소 `169420901`(35,690원)의 상품명·가격·대표 이미지가 모두 맞았다(제출된 6/6). iOS 첫 에이블리 시도는 입력 포커스 오류로 제출되지 않았고 재실행에서 확인했다. 로그의 `503` 및 `If-None-Match`로 이전 규칙을 사용한 경로임을 확인했다. 만료, 앱 재시작, ETag 재확인, 잘못된 응답, 인증 거부는 자동 테스트에 포함했다.

## 상품 ID가 다른 메타데이터 차단

실제 지그재그 HTML 3건에서 상품 URL의 ID는 `product:retailer_item_id`, 상품 JSON-LD의 `sku`, `offers.url`과 일치했다. 해당 형식을 이용해 요청 상품과 다른 JSON-LD 후보는 건너뛰고, 다른 상품 후보만 있을 때는 ID로 확인된 상세 데이터만 사용한다. 페이지 자체의 `product:retailer_item_id`가 다르면 자동 입력하지 않는다. 무신사·에이블리·지그재그 단축 주소도 상품 페이지가 확인된 뒤에는 다른 상품 ID로 바뀌지 않는다.

다른 상품 JSON-LD만 있는 재현 HTML에서는 변경 전 상품명·가격을 잘못 입력했고, 변경 후 입력하지 않았다. 실제 지그재그 HTML 3건은 원래 상품을 읽었고, 테스트용 다른 상품 노드를 앞에 추가해도 결과가 같았다. 각 HTML의 페이지 상품 ID를 바꿨을 때는 자동 입력하지 않았다. 실제 사이트가 다른 상품을 반환했다는 의미는 아니다.

실제 쇼핑몰 단축 링크는 지그재그 `169420901`(35,690원), 에이블리 `51978009`(74,900원), 무신사 `4804589`(24,490원)로 Android·iOS 각각 재검증해 제출된 6/6에서 상품명·가격·대표 이미지가 맞았다. iOS 에이블리 첫 시도는 입력 포커스 실패로 제출되지 않았고 재실행에서 확인했다. Ziper API는 로컬 fixture를 사용했다.

## 기존 상품 주소 형식

운영 서버의 URL 확인은 `http` 상품 주소, 호스트의 마지막 점, 퍼센트 인코딩된 비예약 문자를 정규화한다. 클라이언트는 이 형태를 자동 입력 대상으로 놓칠 수 있었다. 이제 지원몰의 상품 ID를 확인한 경우에만 공식 HTTPS 주소를 만들어 처음부터 그 주소를 연다. `http` 단축 링크, 기본 포트가 아닌 주소, 인코딩된 경로 구분자, 유사 도메인은 허용하지 않는다.

지그재그 HTTP 상품 링크 `169420901`, 무신사에 경로와 상품 ID를 인코딩한 링크 `4804589`, 에이블리 호스트 끝에 점을 붙인 링크 `51978009`를 iOS 시뮬레이터 및 Android 에뮬레이터에서 검증했다. 두 플랫폼 모두 공식 HTTPS 주소로 URL 확인이 요청됐고 재실행까지 포함해 여섯 조합의 이름·가격·대표 이미지가 기대값과 일치했다. 최초 iOS 지그재그 실행은 포커스 오류로 제출되지 않았고, 최초 iOS 무신사는 제출됐지만 자동 입력되지 않았다. 최초 Android 지그재그는 이름과 가격이 맞았지만 캡처에 이미지가 표시되지 않아 완전 성공으로 세지 않았다. Ziper API는 로컬 fixture, 쇼핑몰은 실제 요청을 사용했다.

## 리다이렉트 HTTP 오류와 같은 문서의 앵커

네이티브 양쪽에서 최상위 문서의 HTTP 오류는 URL 갱신보다 먼저 도착할 수 있다. 회귀 테스트에서 리다이렉트 응답에 `403`을 먼저 전달하자 변경 전에는 후속 상품 태그를 잘못 수락했다. 이제 현재 WebView의 최상위 HTTP 오류가 보고되면 URL 갱신 순서와 관계없이 즉시 종료하고, 이후 수신 메시지도 사용하지 않는다. 쇼핑몰에 인위적으로 오류를 유발한 시험은 아니다.

`#reviews`처럼 같은 문서 안에서 이동하는 앵커는 WebView와 페이지 스크립트가 서로 다르게 보고할 수 있다. 메시지 비교에서 `#` 뒤만 제외하고, 상품 ID·출처·경로·쿼리 일치는 그대로 확인한다. 옵션 쿼리가 다른 메시지는 테스트에서 거부했다.

## 최초 규칙 조회의 일시 장애 및 저장 대상 대조

캐시가 없거나 5분이 지난 상태에서 규칙 API의 첫 응답이 `502`·`504`이면 기존 2초 제한 안에서 한 번만 다시 조회한다. `Retry-After`가 보이면 재시도하지 않는다. `503`은 지연 안내를 확인할 수 있는 동일 출처에서만 재시도한다. 배포 서버 CORS는 `Retry-After`를 노출하지 않으므로 교차 출처 `503`과 `429`는 캐시가 없을 때 수동 입력으로 남긴다. 유효한 캐시가 있으면 추가 요청 없이 기존 규칙으로 진행한다.

서버 URL 확인의 정규 주소가 추출 결과와 같은 쇼핑몰·상품을 가리킬 때만 이름·가격·이미지를 폼에 채운다. 같은 상품의 무신사 기존 주소는 통과하고, 다른 상품 번호나 다른 쇼핑몰 주소는 수동 입력으로 남기는 것을 테스트했다.

로컬 시험에서 매 실행 전 규칙 캐시만 지우고 규칙 응답을 `502 → 200`으로 설정했다. 로그에서 제출 6회 모두 캐시 ETag 없이 502를 받은 직후 두 번째 요청으로 복구한 것을 확인했다. 실제 쇼핑몰은 정상 경로로 요청했고 지그재그 `171067691`(103,200원), 무신사 `7561001`(69,900원), 에이블리 `51978009`(74,900원)은 iOS 시뮬레이터와 Android 에뮬레이터에서 각각 이름·가격·대표 이미지가 기대값과 일치했다(제출 6/6). 그전에 Android 지그재그 첫 실행은 Expo 개발 런처에서 멈춰 링크를 제출하지 못했다. 운영 장애 또는 쇼핑몰 장애를 주입한 시험은 아니다.

## 에이블리 공유 카드의 중복 메타데이터

실제 에이블리 `12331299`와 `51978009` 상품 페이지에는 `og:url/title/image`와 `twitter:url/title/image`가 앱·모바일 웹 주소별로 함께 있었다. 같은 주소의 두 블록은 제목·이미지가 같았다. 앱 공유 카드의 이미지는 기존 서버 허용 목록 밖에 있었고, 웹 카드에는 허용된 CDN 이미지가 있었다.

Open Graph 제목·이미지를 읽을 수 없으면 `twitter:url`의 공식 호스트와 상품 ID가 같은 블록만 보조 출처로 사용한다. 허용된 Open Graph 값이 있으면 그대로 우선하고, 가격은 기존 공개 원화 메타데이터에서만 읽는다. 잘못된 상품 ID·유사 도메인·허용되지 않은 이미지·가격 없음은 자동 테스트에 포함했다.

로컬 규칙에서 에이블리 Open Graph 제목·이미지 셀렉터만 일치하지 않게 바꾸고 실제 페이지를 열었다. `12331299` 직접 주소(47,000원)와 `51978009` 단축 주소(74,900원) 모두 Android 에뮬레이터·iOS 시뮬레이터의 4/4 시도에서 이름·가격·대표 이미지가 기존 기대값과 일치했다. 원본 쇼핑몰 문서를 수정하지 않았으며, Ziper 운영 규칙이나 실제 장애의 재현은 아니다. 에이블리 공개 가격 자체가 없거나 페이지가 거부되면 여전히 완전 자동 입력하지 않는다.

원래 규칙으로 복원한 뒤 에이블리 앱 주소 `13519743`(26,800원), 무신사 기존 앱 주소 `4804589`(24,490원), 지그재그 제휴 단축 주소 `171067691`(103,200원)을 다시 실행했다. 두 플랫폼에서 각각 3/3이 상품명·가격·실제로 로드된 이미지까지 일치했다. 독립 웹에서 에이블리 주소는 수동 입력만 안내했고, 네트워크 기록에는 Ziper URL 확인과 보드 조회만 있었으며 추출 규칙·쇼핑몰 요청은 없었다.

## 상품 주소 보고가 늦는 리다이렉트

실제 Android 무신사 OneLink에서 상품 문서와 메타데이터가 `onLoadStart`·`onLoad`의 최종 URL 보고보다 앞선 경우가 있었다. 이 상황에서 진행 이벤트도 먼저 도착하고 문서 시작 주입을 놓치는 순서를 재현하니, 기존 코드는 신뢰할 수 있는 상품 URL이 진행 이벤트에 있어도 스캔을 시작하지 않았다. 이제 진행 이벤트에 이미 허용된 HTTPS 상품 URL이 있으면 스캔을 일찍 주입한다. 진행 이벤트나 메타데이터만으로 상품을 확정하지 않고, 기존 최종 URL과 상품 ID 대조는 그대로 수행한다. 단축 주소 자체·일반 페이지·다른 쇼핑몰에는 이 경로로 주입하지 않는다. 두 플랫폼의 라우터 테스트에서 이벤트 순서를 재현해 이 차이를 확인했다.

실제 링크 4개(무신사 OneLink 2종, 에이블리 단축, 지그재그 제휴)를 각 플랫폼에서 실행해 최초 제출 8건 중 6건이 상품명·가격·대표 이미지까지 일치했다. Android 무신사 `4804589`와 iOS 에이블리 `51978009` 첫 제출은 수동 전환됐다. iOS 실패 화면에는 QA 로그를 추가하던 중 개발 앱의 새로고침이 겹쳐 원인을 분리하지 못했다. 로그를 추가한 iOS 에이블리 재실행, 로그를 제거한 최종 코드의 iOS 에이블리와 Android 지그재그 재실행은 모두 성공했다. 재실행 결과는 최초 실패를 대체하지 않는다. Ziper API는 기존 로컬 fixture를 사용했다.

Android 무신사 `4804589`를 임시 로그로 추적한 별도 시험에서, 단축 주소가 정상적으로 공식 상품 페이지를 열었지만 해당 페이지가 최상위 HTTP `403`을 반환하는 것을 확인했다. 같은 단축 주소 3회 중 2회는 정상 자동 입력, 1회는 `403`으로 실패했고, 공식 직접 주소 1회도 `403`으로 실패했다. 성공 2회 중 한 번은 메타데이터가 URL 보고보다 먼저 와 기존 대기 로직을 탔다. 이번 로그는 모든 실패가 같은 원인이라는 증거나 새 진행 이벤트 주입만으로 복구됐다는 증거는 아니다. 접근 거부는 자동 재시도하거나 우회하지 않는다.

## 첫 상품을 읽는 중 다른 링크로 바꿀 때

등록 화면 안에서 뒤로 가면 웹은 이전 결과를 기다리지 않지만, 네이티브 WebView는 상품을 계속 읽을 수 있다. 기존에는 그 사이에 다시 제출한 링크를 읽지 않고 수동 입력으로 보냈다. 이제 새로 제출한 유효 링크가 이전 작업을 종료하고 새 WebView를 연다. 같은 URL을 다시 제출해도 이전 WebView를 재사용하지 않으며, 이전 요청의 상품 메시지나 HTTP 오류가 늦게 도착해도 새 폼에 영향을 주지 않는다. iOS·Android 라우터 테스트에서 같은 주소와 다른 주소 재제출을 모두 검증했다.

Android 에뮬레이터에서 에이블리 `12331299`를 읽는 도중 화면을 닫고 곧바로 지그재그 `171190375`를 제출했다. 첫 작업이 충분히 오래 남도록 로컬 규칙에서만 에이블리의 추출 필드를 비웠다. 두 번째 제출은 첫 요청의 8초 제한 전에 시작했다. 이전 동작은 지그재그의 빈 수동 폼으로 전환됐고, 수정 후 같은 흐름은 지그재그 상품명·34,200원·대표 이미지가 일치했다. 쇼핑몰 페이지는 실제로 열었으며 Ziper API는 로컬 fixture였다.

일반 규칙으로 복원한 뒤 지그재그 `171926018`(55,200원), 무신사 `7561001`(69,900원), 에이블리 `13519743`(26,800원)의 직접 링크를 각 플랫폼에서 한 번씩 재검증했다. 6/6의 상품명·가격·실제로 로드된 대표 이미지가 기대값과 일치했다. 이 결과에도 실기기와 운영 API가 포함되지는 않는다.

## 지그재그 상세 표시 가격 보완

실제 지그재그 상세 HTML에서 `getPdpBaseInfo.product.product_price`의 `display_final_price`를 공개 상품 JSON-LD 가격과 비교했다. `171190375`와 `169420901`은 추가 표시가(첫구매쿠폰)가 공개 가격과 같고, `171067691`은 추가 표시가가 없어 기본 표시가가 공개 가격과 같았다. 이 값은 누구나 보게 되는 결제 확정가를 의미하지 않는다.

기존 메타데이터·할인 가격 필드가 비어 있으면, 요청 주소와 ID가 일치하는 상세 상태에서만 원화 표시가로 보완한다. 추가 표시가가 있으면 기본 표시가보다 먼저 확인한다. 통화가 `원`이 아니거나 원화 표시 가격을 확인하지 못하면 가격을 추정하지 않으며, 정가(`max_price_info`)를 대신 채우지 않는다.

보관한 실제 HTML 3건의 상태에서 기본 메타데이터와 `final_discount_info`를 제외하고 스캔했다. 기존 코드는 3건 모두 가격을 비워 뒀고, 수정 후 상품명·가격(34,200원 / 35,690원 / 103,200원)·대표 이미지 경로가 원본 공개 상품 데이터와 3/3 일치했다. 이것은 저장된 HTML에서 보완 경로만 분리한 시험으로, 실제 쇼핑몰에서 그 필드가 사라진 것을 관측한 것은 아니다.

일반 규칙으로 실제 링크 네 건(지그재그 직접 `171190375`와 제휴 `171067691`, 무신사 OneLink `6623590`, 에이블리 앱 주소 `13519743`)을 Android 에뮬레이터·iOS 시뮬레이터에서 각각 한 번씩 열었다. 8/8에서 상품명·가격·실제 대표 이미지가 기대값과 맞았다. 이 검증은 일반 경로의 회귀 확인이며, Ziper API는 로컬 fixture였다.

## 무신사 구조화 데이터의 상품 ID 대조

실제 무신사 `6623590`과 `7561001`의 WebView에서 JSON-LD `sku`, 상품 `url`, `offers.url`이 현재 상품 번호와 일치했고 `og:url`도 동일 상품이었다. 이제 지그재그처럼 구조화 데이터에 상품 식별자가 있으면 링크의 상품과 대조한다. 다른 상품 노드만 있다면 동일 상품으로 확인되는 OG 태그나 검증된 상세 상태를 사용한다. `og:url` 자체가 다른 상품이면 해당 페이지 태그를 사용하지 않는다.

재현 테스트에서 무신사 JSON-LD의 첫 노드로 추천 상품을 놓자 기존 코드는 다른 상품을 채웠다. 수정 후에는 동일 상품 노드만 사용하고, 잘못된 판매 URL이나 다른 상품의 OG 제목·가격·이미지는 제외했다. 이는 테스트로 재현한 오입력 조건이며 무신사 실제 페이지가 추천 상품을 잘못 게시했다는 뜻은 아니다.

최종 코드로 무신사 직접 `7561001`(69,900원)·OneLink `6623590`(239,200원), 지그재그 제휴 `171067691`(103,200원), 에이블리 직접 `13519743`(26,800원)을 다시 확인했다. 두 플랫폼에서 제출된 8/8의 상품명·가격·대표 이미지가 일치했다. 최초 iOS 무신사 OneLink 시도는 입력 포커스 오류로 미제출, 별도 재실행은 성공했다. 수정 전 Android 무신사 직접 링크 추적은 제출됐지만 빈 폼으로 전환됐으며 실패 원인은 확인되지 않았다. 쇼핑몰은 실제 요청, Ziper API는 로컬 fixture였다.

## 무신사 쿠폰가와 공개 상품 가격 구분

무신사 나이키 공개 브랜드 목록에서 새 상품을 확인했다. `3976349`는 목록에 134,100원이었지만 정상 앱 WebView의 상세 페이지에서 Open Graph와 JSON-LD는 모두 149,000원이었다. 같은 상품의 확인된 상세 데이터에서 `salePrice`는 149,000원, `couponPrice`와 `finalPrice`는 134,100원, `couponDiscount`는 `true`였다. 목록에서 보이는 쿠폰 적용가와 공개 상품 메타데이터는 기준이 같지 않다.

이전에는 가격 태그가 없을 때 `finalPrice`로 보완해 같은 상품의 가격이 달라질 수 있었다. 이제 상세 데이터에서 원화 `salePrice`를 우선 사용하고, 쿠폰 적용이 명시됐는데 `salePrice`가 없으면 쿠폰가로 추정하지 않는다. 공개 상품 메타데이터의 우선순위는 바꾸지 않는다. 사용자별 결제가는 검증 범위가 아니다.

로컬 Ziper 규칙에서 무신사의 가격 셀렉터만 비우고 실제 상품 페이지 두 개를 다시 열었다. `3976349`(149,000원), `5705621`(167,200원)의 상세 데이터 폴백이 양쪽 플랫폼에서 일반 경로와 같은 가격을 채웠으며, 상품명과 대표 이미지도 일치했다(4/4). 앞선 일반 규칙 검증에서는 이 두 주소와 지그재그 HTTP `169420901`(35,690원), 에이블리 모바일 `13519743`(26,800원)의 양쪽 플랫폼 8/8이 공개 상품 기준과 맞았다. Ziper API는 로컬 fixture였다. 별도 데스크톱 브라우저에서 연 무신사 `4566724`는 403이었고 앱 시도 수에 포함하지 않았다.

## 상품 WebView 렌더러 종료 대응

상품을 읽는 WebView의 렌더러가 종료되면 기존에는 추출 제한 시간이 지나기를 기다렸다. 이제 이미 확인된 동일 HTTPS 상품에 한해, 기존 제한 시간과 연결 오류와 공유하는 1회 재시도 한도 내에서 WebView를 새로 만든다. 미해결 단축 링크, 재시도 소진, 접근 거부는 다시 요청하지 않는다. 두 플랫폼의 네이티브 콜백을 테스트에서 재현해 복구와 기존 WebView의 늦은 이벤트 무시를 검증했다. 실기기 렌더러나 전체 앱 프로세스를 종료한 실험은 아니다.

## 제한 시간까지 확인한 부분 정보 보존

같은 상품 문서를 읽는 동안 제목과 가격이 들어온 뒤 제목만 들어오면, 기존 코드는 가격을 버렸다. 이제 새 결과에 추가되거나 바뀐 값이 없다면 더 많은 필드가 확인된 앞선 결과를 유지한다. 두 응답의 필드를 섞지는 않는다. 새 값이 확인되면 새 응답으로 교체하고, 경로 또는 쿼리가 바뀌면 이전 부분 결과를 폐기한다. 페이지 내 앵커 변경만으로는 폐기하지 않는다.

iOS·Android 라우터 테스트에서 부분 응답의 가격 `0원` 보존, 실제 값 변경, `?option=` 전환을 재현했다. 완전 자동 입력으로 분류하지 않으며, 이 테스트는 실제 매장에서 해당 이벤트 순서가 얼마나 자주 발생하는지 측정하지 않는다. 일반 경로 회귀에서는 지그재그 제휴 `169420901`(35,690원), 무신사 직접 `5705621`(167,200원), 에이블리 추적·앵커 `12331299`(47,000원)의 양쪽 플랫폼 6/6에서 이름·가격·대표 이미지가 일치했다. 쇼핑몰은 실제 요청, Ziper API는 로컬 fixture였다.

## 무신사 대표 이미지의 상품 번호 대조

공개 무신사 상품 이미지에서 `image.msscdn.net/images/goods_img/<날짜>/<상품 번호>/…`와 `thumbnails/images/goods_img/…` 형식을 확인했다. 이 형식에 들어 있는 상품 번호가 요청 상품과 다르면, CDN이 허용 목록에 있어도 해당 이미지 후보는 제외한다. 대표 메타데이터 대신 상세 쿼리를 읽을 때도 같은 검증을 적용하고, 검증된 `Detail` 항목의 이미지로 보완한다. 이미지 호스트 허용 목록은 바뀌지 않았다.

회귀 테스트에서 요청 상품 `4804589`의 메타 태그에 `6623590` 이미지 주소를 넣었을 때 이전 코드는 다른 상품의 이미지를 채웠다. 수정 후 같은 상품의 상세 이미지를 채우고, 대체 후보도 검증을 통과하지 못하면 이름·가격만 남겼다. 실제 쇼핑몰이 잘못된 이미지를 게시했다는 뜻은 아니다.

Android 에뮬레이터·iOS 시뮬레이터에서 무신사 `3976349`(149,000원)·`5705621`(167,200원), 지그재그 제휴 `171067691`(103,200원), 에이블리 단축 `51978009`(74,900원)를 열어 8/8에서 상품명·가격·대표 이미지가 기대값과 일치했다. 별도로 로컬 무신사 이미지 셀렉터만 비우고 두 무신사 상세 페이지를 다시 열었을 때도 실제로 표시된 대표 이미지가 원래 규칙의 결과와 일치했다(4/4). 이 시험에서 `Detail`과 페이지 메타데이터에 서로 다른 이미지가 게시된 상태를 만들지는 않았다. Ziper API는 로컬 fixture였다.

## 지그재그 공개 메타 태그의 상품 주소 대조

보관한 지그재그 상품 HTML 3건(`171190375`, `169420901`, `171067691`)에서 `og:url`은 해당 상품의 공식 URL이었다. 이제 지그재그도 무신사처럼 `og:url`을 상품 ID와 대조한다. 태그가 다른 상품을 가리키면 해당 제목·가격·이미지는 사용하지 않고, 동일 상품임을 확인한 구조화 데이터나 상세 상태만 사용한다. 상품 ID가 다른 구조화 데이터만 있어도 올바른 `og:url`이 있는 공개 태그는 사용할 수 있다.

보관한 실제 HTML로 두 조건을 재현했다. 같은 상품의 공개 태그와 다른 상품의 JSON-LD만 남기자 수정 전 3건 모두 정보를 놓쳤고, 수정 후 3건 모두 상품명·가격·이미지 URL이 원본과 일치했다. 반대로 `og:url`을 다른 상품으로 바꾸고 검증된 구조화 데이터를 제거하자 기존 코드는 3건 모두 채웠고, 수정 후에는 3건 모두 거부했다. 이는 구조를 바꾼 재생 시험이며, 실제 쇼핑몰이 잘못된 태그를 게시한 것으로 집계하지 않았다.

일반 규칙으로 다시 연 지그재그 직접 `171190375`(34,200원)·제휴 `171067691`(103,200원), 무신사 직접 `5705621`(167,200원), 에이블리 단축 `51978009`(74,900원)는 iOS 시뮬레이터와 Android 에뮬레이터의 8/8에서 상품명·가격·실제 대표 이미지가 맞았다. Android에서 지그재그 없는 상품 `1234567`과 에이블리 이벤트 `trcogi0`는 모두 빈 수동 입력으로 남았다. Ziper API는 로컬 fixture였다.

## JSON-LD 이미지 형식과 옵션 가격

세 쇼핑몰 규칙이 공통으로 사용하는 `ldjson:image[0]`은 기존에 배열의 첫 요소가 문자열인 경우만 읽었다. 이제 단일 URL과 이미지 객체도 읽되, CDN 및 상품 ID 검증은 유지한다. `39000.00`처럼 소수부가 전부 0인 값은 39,000원으로 읽고, 실제 소수 금액은 반올림하지 않는다. `ldjson:offers.price`에 유효한 원화 가격이 여러 개이고 서로 다르면 첫 값을 임의로 쓰지 않는다. 그때는 확인된 다른 출처가 없으면 가격을 비운다.

보관한 실제 지그재그 JSON-LD 3건(`171190375`, `169420901`, `171067691`)의 원본은 변경 전후 모두 동일하게 처리했다. 이미지를 단일 URL로, 가격을 `.00` 표기로 바꾼 재생에서는 기존 0/3에서 수정 후 3/3으로 복구했다. 서로 다른 원화 가격을 추가한 재생에서는 기존 3/3이 첫 가격을 골랐고, 수정 후 3/3이 가격을 비웠다. 관측된 실제 마크업 장애가 아니라 형식 변화를 시험한 결과다.

일반 규칙으로 지그재그 제휴 `169420901`(35,690원), 무신사 직접 `3976349`(149,000원), 에이블리 앱 주소 `13519743`(26,800원)을 다시 열었다. iOS 시뮬레이터·Android 에뮬레이터 6/6에서 상품명·가격·실제로 표시된 대표 이미지가 기존 기대값과 일치했다. 실제 쇼핑몰을 요청했으며, Ziper API는 로컬 fixture였다.

## 늦게 도착한 단축 링크 상품 페이지

기존 추적 로그에서 에이블리 추출이 약 5.8초, 무신사 OneLink가 약 6.3초 걸린 정상 사례가 있었다. 이전에는 단축 링크 이동과 상품 추출에 같은 8초를 사용했다. 이제 8초 이내에 지원몰의 상품 주소를 처음 확인하면 상세 페이지를 읽을 시간을 최대 6초까지 확보하되, 전체는 12초를 넘기지 않는다. 직접 링크와 상품 주소를 확인하지 못한 단축 링크는 기존 8초를 유지한다. 추가 이동으로 제한 시간이 다시 늘어나지 않으며, 접근 거부는 즉시 수동 입력으로 전환한다.

라우터 시간 제어 테스트에서 7초에 상품 주소, 10초에 상품 정보를 전달했다. 기존 코드에서는 이 결과를 잃었고 수정 후 두 플랫폼에서 받았다. 미해결 링크의 8초 제한, 확인 후 12초 상한, 403이면 즉시 종료하는 경우도 검증했다. 실제 WebView의 시간 초과 빈도가 얼마나 줄었는지는 이 시험으로 추정하지 않는다. 일반 규칙으로 지그재그 제휴 `171067691`(103,200원), 무신사 OneLink `6623590`(239,200원), 에이블리 단축 `51978009`(74,900원)을 양쪽 플랫폼에서 확인했다. 6/6의 상품명·가격·실제 대표 이미지가 맞았다. 쇼핑몰은 실제 요청을 보냈고 Ziper API는 로컬 fixture다.

## 보드 조회 장애 시 자동 입력 보존

상품 URL 확인과 추출이 끝나면 보드 목록을 기다리지 않고 상품 폼을 보여 준다. 보드 조회 오류 또는 8초 시간 초과는 보드 영역에서만 표시한다. 재시도는 보드만 다시 요청하며, 상품명·가격·이미지와 입력 중인 값을 유지한다. 보드 확인 전에는 저장이나 보드 생성을 허용하지 않는다.

Ziper 테스트 API에서 첫 보드 요청만 `503`, 이후 요청은 `200`으로 응답하게 했다. Android 에뮬레이터의 무신사 `3976349`(149,000원), iOS 시뮬레이터의 에이블리 `13519743`(26,800원)은 보드 오류 중에도 실제 쇼핑몰에서 가져온 이름·가격·대표 이미지가 보였다. 양쪽 모두 재시도 후 보드가 표시됐고, 상품 URL 확인은 시도당 1회, 보드 조회는 `503 → 200` 2회였다. 시간 초과와 재시도 후 편집값이 저장 요청에 유지되는 경우는 컴포넌트 테스트로 확인했다. 실제 운영 저장 요청은 보내지 않았다.

## 상품 상세 페이지 게이트웨이 오류

기존에는 WebView가 최상위 문서의 HTTP 오류를 받으면 즉시 자동 입력을 종료했다. `502`·`504`는 이미 확인된 동일 HTTPS 상품 주소에서 발생하고 제한 시간이 1.5초 이상 남은 경우에만 한 번 더 읽는다. 연결 오류·렌더러 종료와 한 번의 재시도 한도를 공유하며, 다른 상품·미해결 단축 링크·`403`·`429`·`503`은 재시도하지 않는다.

iOS·Android의 WebView 오류 콜백을 모킹해 확인된 주소의 `502`·`504` 이후 정상 상품 응답, 같은 오류 반복, 무신사 단축 링크에서 상품 주소 확인 전후, 다른 상품 주소, 시간 부족과 접근 제한을 검증했다. 실제 쇼핑몰에서 `502`·`504`를 관찰하거나 재현한 시험은 아니다.

## 상품 URL 확인 API의 일시 장애

배포 코드에서 `POST /api/v1/products/url-check`는 외부 쇼핑몰 요청이나 쓰기가 없는 정규화·중복 조회다. `502`·`504`를 받으면 같은 URL을 한 번만 다시 확인하며, 전체 5초를 공유한다. 확인 가능한 `Retry-After`, 접근 거부와 요청 제한 응답은 자동 재시도하지 않는다. 다시 확인할 때도 서버의 상품 주소·중복 판정을 따른다. 상품 저장 요청은 재시도하지 않는다. 테스트에서 재시도 전에는 추출이 끝나도 URL 확인 오류가 화면을 막았으며, 변경 후에는 추출을 한 번만 하고 서버 확인을 복구했다.

실제 쇼핑몰 페이지와 로컬 Ziper API를 사용하고, 상품·플랫폼마다 최초 URL 확인 응답만 `502`로 주입했다. 지그재그 `137746998`(55,390원), 무신사 OneLink → `6623590`(239,200원), 에이블리 `13848135`(11,340원)에서 양쪽 플랫폼의 첫 제출 6/6건이 이전에 확인한 이름·공개 가격·대표 이미지와 일치했다. API 로그에서 각 제출이 같은 주소로 `502 → 200`을 받은 것을 확인했다. 별도 미존재 지그재그 `1234567`은 Android에서 입력값이 비었고, 독립 웹에서는 재시도 후에도 상품 페이지·규칙 요청 없이 수동 입력으로 진행했다. 운영 URL 확인 장애를 재현한 것은 아니다.

## 에이블리 구조화 데이터와 상품 ID 대조

에이블리의 JSON-LD `Product` 후보에서도 상품 번호를 확인한다. SKU, 공식 상품 주소 또는 판매 제안 주소에서 같은 상품임을 확인한 후보만 쓰며, 앞선 추천 상품이나 주소가 충돌하는 후보는 제외한다. 기존 Open Graph·Twitter 카드 경로와 CDN 허용 목록은 그대로 유지한다.

회귀 테스트에서는 `13519743`의 정상 상품명과 추천 `51978009`의 74,900원·이미지가 잘못 합쳐지는 상황을 재현했다. 수정 후에는 같은 상품의 26,800원·이미지를 사용했다. 다른 상품만 있거나 판매 제안 주소가 충돌하거나 상품을 식별할 수 없을 때는 확인된 상품명만 남았다. 이는 인위적으로 만든 구조화 데이터 사례이며, 에이블리의 실제 응답에서 추천이 먼저 나온 사례를 관찰한 것은 아니다.

실제 상품 페이지와 로컬 Ziper API로 에이블리 앱 주소 `13848135`(11,340원), 단축 링크 `51978009`(74,900원), 지그재그 제휴 `169420901`(35,690원), 무신사 직접 주소 `5705621`(167,200원)을 열었다. iOS 시뮬레이터·Android 에뮬레이터 첫 제출 8/8건의 상품명·가격·실제 표시 이미지가 이전에 확인한 값과 같았다. 별도로 Android의 에이블리 이벤트와 지그재그 만료 링크는 상품 정보 없이 수동 입력으로 끝났다.

## 가격 메타 태그가 여러 개일 때

`product:price:amount`의 유효한 원화 값이 하나일 때만 사용한다. `39,000`과 `39000.00`처럼 표기만 다른 중복은 허용한다. 서로 다른 값이 나오거나 통화 태그에 외화가 섞이면 이 가격 출처를 건너뛰고, 같은 상품으로 확인한 JSON-LD나 상세 데이터가 있으면 사용한다. 다른 출처에서도 확인되지 않으면 가격은 비워 둔다.

보관된 지그재그 상세 HTML `169420901`(35,690원)·`171067691`(103,200원)에서 원본 결과는 그대로였다. 앞에 다른 가격이나 KRW·USD 혼합 태그를 추가한 재현 4건에서는 기존 코드가 첫 가격을 골랐고 수정 후 정상 가격으로 복구했다. 실제 쇼핑몰에서 가격 태그 충돌을 관찰한 것은 아니다.

일반 규칙으로 지그재그 제휴 링크 `171067691`(103,200원), 무신사 직접 주소 `3976349`(149,000원), 에이블리 추적 주소 `12039665`(23,560원)를 열었다. Ziper API만 로컬 fixture를 사용했으며 iOS 시뮬레이터·Android 에뮬레이터 첫 제출 6/6건의 상품명·공개 가격·실제 표시 이미지가 이전에 확인한 상품과 일치했다.

## 에이블리 공유 카드 제목에서 쇼핑몰 표기 제거

에이블리 공유 카드의 Open Graph·Twitter 제목에는 상품명 뒤에 ` - 에이블리`가 붙는 경우가 있다. 예를 들어 실제 상품 상세의 `12039665` 제목에는 이 접미사가 없으며, 판매자 입력과 쇼핑몰 표기가 별개다. 기존 제목 우선순위를 유지하고 카드 제목 끝의 쇼핑몰 표기만 한 번 제거한다. 상품명 가운데의 ` - 에이블리`와 JSON-LD 이름은 변경하지 않는다.

## 지그재그 상세 데이터 가격의 통화와 값 검증

공개 메타 태그로 가격을 확인하지 못해 상품 상세 데이터로 복구할 때, 화면 가격이 외화로 표시되면 통화가 없는 할인 필드도 원화로 해석하지 않는다. 할인 필드가 음수·소수 등 유효하지 않은 값이면 상품 상세의 원화 표시가를 사용한다. 확인된 다른 가격 출처와 대표 이미지에는 영향을 주지 않는다.

보관한 지그재그 `169420901`·`171067691` 상세 데이터에서 원본 가격은 기존과 동일했다. 할인 필드에 음수를 넣은 재현 2건은 정상 원화 표시가로 복구했고, 외화 표시와 통화 없는 할인 숫자를 함께 넣은 재현 2건은 가격을 비웠다. 이 변형은 실제 쇼핑몰 장애를 관찰한 것이 아니다.

실제 링크로 지그재그 제휴 `169420901`(35,690원), 무신사 OneLink → `4804589`(24,490원), 에이블리 앱 주소 `13848135`(11,340원)를 확인했다. 로컬 Ziper API를 둔 iOS 시뮬레이터·Android 에뮬레이터에서 첫 제출 5/5건의 가격·표시 이미지·화면에서 확인 가능한 이름이 기존에 검증한 상품과 일치했다. 최초 iOS 지그재그는 입력 포커스 오류로 미제출이었고, 별도 재실행 1/1건이 일치했다. ## 규칙 응답 본문이 전송 중 끊길 때

규칙 API가 `200`을 보낸 뒤 본문 연결이 끊기면 유효한 규칙을 확인한 것이 아니다. 전송 실패로 분류해 이전에 검증한 규칙이 5분 이내인 경우에만 사용한다. 실패 응답으로 캐시 시각이나 ETag를 갱신하지 않는다. 본문을 모두 읽었지만 JSON이나 스키마가 잘못된 경우와 `401`·`403`은 기존처럼 캐시를 비운다. 테스트에서 이전 구현은 본문 읽기 실패도 잘못된 JSON으로 처리해 유효한 캐시를 지웠다.

로컬 Ziper API가 캐시 ETag를 받은 경우 실제로 `200` 헤더와 본문 일부를 전송한 뒤 연결을 닫았다. 쇼핑몰 페이지는 실제 WebView가 열었고, fixture는 상품 데이터를 제공하지 않았다. 지그재그 `169420901`(35,690원), 무신사 `3976349`(149,000원), 에이블리 `51978009`(74,900원)을 검증했다. Android에서는 에이블리 `13848135`로 캐시를 준비했다. iOS의 준비 시도는 입력 포커스 오류로 미제출이어서 첫 지그재그 제출이 대신 캐시를 준비했다. 초기 정상 규칙 응답과 본문 절단 응답은 API 로그에서 구분했다. 본문 절단 조건의 첫 제출은 Android 3/3, iOS 2/2에서 상품명(화면 표시 부분), 가격, 대표 이미지가 이전 검증값과 일치했다. iOS 지그재그는 절단 조건에서 별도 재실행해 1/1 일치했다. 정상 규칙을 받은 캐시 준비 제출과 미제출 포커스 오류는 장애 조건 집계에서 제외했다.

## 지그재그 구형 가격 필드의 상품 번호 대조

배포 규칙의 `__NEXT_DATA__.props.pageProps.product.final_price`는 상세 경로, 페이지 데이터의 `catalog_product_id`, 가격이 들어 있는 `product.id`가 모두 같은 상품을 가리킬 때만 사용한다. 공개 메타 태그·JSON-LD 가격의 우선순위는 그대로다. 구형 값이 다른 상품의 것이거나 식별할 수 없으면 이미 검증하는 `getPdpBaseInfo` 상세 데이터로 넘어간다.

보관한 `169420901`·`171067691` 상세 페이지는 원본 결과가 그대로였다. 같은 두 페이지에서 공개 가격 태그만 빼고 다른 상품의 `final_price`를 추가하자 기존 코드는 두 건 모두 1원을 선택했고, 변경 후에는 현재 상품의 기존 가격(35,690원·103,200원)을 사용했다. 현재 상품 번호가 맞는 구형 데이터도 두 건 모두 읽었다. 구형 블록을 덧붙인 결과는 재현 테스트이며 실제 쇼핑몰이 잘못된 가격을 보낸 사례는 아니다.

## 규칙 조회 중 로그인 갱신 지연

규칙 요청이 `401`을 받아 공유 토큰 갱신을 기다리는 동안에도 규칙 조회의 2초 제한을 적용한다. 취소된 규칙 요청은 갱신 완료 후 다시 전송하지 않는다. 토큰 갱신 자체는 취소하지 않으며, 상품 URL 확인 등 다른 요청이 같은 갱신 결과를 사용할 수 있다.

시간 제어 테스트에서 두 요청 모두 최초 `401`, 토큰 갱신은 4초 뒤 성공하도록 했다. 수정 전에는 규칙 단계가 2초 이후에도 URL 확인으로 넘어가지 않았다. 수정 후 URL 확인은 2초에 시작해 기존 갱신에 합류했고, 새 토큰으로 URL 확인만 재전송했다. 이 시험에서는 규칙 캐시가 없어서 수동 입력으로 이어졌다. 운영 인증 시험은 아니다.

일반 응답에서는 지그재그 제휴 `169420901`(35,690원), 무신사 OneLink → `4804589`(24,490원), 에이블리 추적 주소 `12331299`(47,000원)의 첫 제출 6/6건에서 화면 표시 이름·가격·대표 이미지가 일치했다(iOS 시뮬레이터·Android 에뮬레이터, 로컬 Ziper API). ## 리다이렉트 진행 이벤트와 상품 문서 확인 사이의 경합

Android 무신사 OneLink → `4804589`의 앞선 실패 두 건을 다시 조사했다. 임시 로그를 붙인 시험은 같은 단축 주소 3/3, 다른 무신사 OneLink(`6623590`) 1/1, `4804589`의 공식 직접 주소 1/1이 일치했다. iOS에서도 같은 단축 주소 1/1이 일치했다. 한 Android 제출은 3.68초에 상품 메시지가 먼저 도착했고, 약 7ms 뒤 공식 상품 주소를 보고한 후 수락했다. 이번 추적에서 Android 실패나 `403`은 재현되지 않아 앞선 실패의 원인은 미확인이다. 임시 로그는 제품 코드에 포함하지 않았다.

진행 이벤트에서 새 주소가 먼저 보여도 해당 문서가 아직 활성화되지 않았으면 주입한 스크립트가 이전 페이지에서 끝날 수 있다. 최상위 상품 주소가 나중에 보고될 때, 같은 주소로 진행 이벤트에서 먼저 주입했다면 상품 스캔을 다시 요청한다. 중복 실행은 문서 안에서 차단하며, 새 요청이나 시간 연장 없이 기존 WebView에서만 실행한다. 단축 링크에서 이 이벤트 순서와 로드 완료가 오지 않는 경우를 콜백 테스트로 재현했다. 수정 전 iOS·Android에서 모두 두 번째 주입이 없었고, 수정 후 양쪽에서 상품명·가격·이미지를 받았다. 이 보완이 앞서 관측한 무신사 실패를 해결했다고 보지는 않는다.

추적 로그를 제거한 최종 코드에서 무신사 OneLink `4804589`(24,490원), 에이블리 단축 `51978009`(74,900원), 지그재그 제휴 `169420901`(35,690원)을 검증했다. 각 링크의 iOS 시뮬레이터·Android 에뮬레이터 첫 제출 6/6건이 화면 표시 이름·가격·대표 이미지까지 일치했다. 쇼핑몰은 실제 요청이며 Ziper API만 로컬 fixture를 사용했다. 임시 로그가 있는 시험과 합산하지 않았다.

## 같은 주소에서 먼저 받은 완전한 결과 유지

최종 주소를 기다리는 동안 같은 문서의 이름·가격·이미지를 받았다가, 값 변화 없이 이미지 필드만 빠진 메시지를 다시 받으면 기존에는 이미지가 없는 결과를 적용했다. 이제 대기 중인 메시지에도 확정된 문서와 같은 판단을 적용한다. 새 메시지가 필드를 추가하거나 기존 값을 바꾸면 새 결과 전체를 쓰고 두 결과를 합치지 않는다. 가격 39,000원과 이미지가 먼저 온 뒤 이미지가 빠지는 경우, 그리고 새 가격 18,000원이 오면서 이미지가 빠지는 경우를 iOS·Android 콜백으로 검증했다. 두 경우 모두 최종 문서 일치 검증은 유지했다.

일반 규칙으로 무신사 OneLink `4804589`·구형 `312889`, 에이블리 단축 `51978009`, 지그재그 추적+앵커 `137746998`을 iOS 시뮬레이터와 Android 에뮬레이터에 한 번씩 제출했다(실제 쇼핑몰, 로컬 Ziper API). 8/8건에 가격·대표 이미지와 화면에 보이는 상품명이 채워졌다. 전체 제목 대조에서 아래 접미사 문제를 찾았으므로 이 결과를 8/8 정확도로 해석하지 않는다. 독립 웹에서는 에이블리 단축 주소로 URL 확인과 보드만 요청했고, 쇼핑몰이나 추출 규칙을 요청하지 않았다.

## 무신사 공유 제목의 후기 접미사 제거

Android 에뮬레이터에서 구형 링크 `312889`의 전체 상품명을 대조하자, 노출된 가격(59,800원)과 이미지는 맞았으나 상품명 끝에 `- 사이즈 & 후기 | 무신사`가 붙었다. 이전 무신사 `4804589` 공개 메타 태그 로그에서는 `- 후기 | 무신사`가 확인됐다. 두 접미사만 무신사 Open Graph 또는 문서 제목 끝에서 제거한다. 판매자 제목의 중간 문구나 구조화 데이터의 이름은 건드리지 않는다.

수정 후 Android에서 `312889` 구형 주소와 `4804589` OneLink를 별도로 다시 제출해 전체 이름, 가격 및 대표 이미지가 2/2건 일치했다. iOS에서는 별도 `312889` 재실행의 표시 이름·가격·대표 이미지가 일치했지만 캡처로 긴 제목 끝은 검증하지 못했다. 수정 전 전체 제목 불일치는 별도로 보존한다.

## 에이블리 브라우저 제목 폴백에서 판매자·스토어 표기 제거

별도로 연 에이블리 상품 상세 화면의 `13848135` 상품명은 `[당일출고][MADE/6color]피크닉 트윌 오버핏 남방 셔츠`였지만, 로컬 규칙에서 제목 출처를 브라우저 제목으로 제한하면 Android 등록 폼의 전체 값에 `베이델리`와 ` - 에이블리 스토어`가 붙었다. 브라우저 제목을 사용할 때만 이 접미사를 제거하고, 요청 상품 번호와 `product:retailer_item_id`가 일치하며 `product:brand`가 정확히 접두사와 맞을 때만 판매자명을 제거한다. `상품 상세 - 에이블리 스토어`는 상품명으로 사용하지 않는다. 공유 카드·JSON-LD 제목과 가격·이미지 규칙은 변경하지 않았다.

## 에이블리 공유 카드 주소가 충돌할 때

에이블리 페이지의 Open Graph 주소가 현재 상품과 다르더라도, 같은 상품으로 확인된 Twitter 카드나 JSON-LD까지 모두 버리지 않는다. 충돌한 Open Graph 제목과 이미지는 사용하지 않는다. 일치한 Twitter 카드로 복구하는 경우 공용 가격 태그는 `product:retailer_item_id`가 현재 상품을 확인할 때만 사용한다. 가격을 확인할 수 없으면 이름과 이미지가 있어도 부분 입력으로 남는다.

이전에 수집한 `12331299`·`51978009` 카드 태그를 재생했다. 원본에서는 두 상품의 결과가 그대로였다. Open Graph 주소를 다른 상품으로 바꾼 조건에서는 이전 코드가 결과를 보내지 않았고, 수정 후에는 두 상품 모두 같은 상품의 Twitter 카드와 확인된 가격을 사용했다. 상품 번호 태그를 빼면 가격만 비웠다. 주소 충돌은 변형 시험에서 만든 조건으로, 실제 에이블리 응답에서 관찰한 것은 아니다.

일반 규칙으로 에이블리 단축 `51978009`(74,900원), 무신사 OneLink → `4804589`(24,490원), 지그재그 직접 `137747413`(79,610원)을 열었다. 실제 쇼핑몰을 요청했고 Ziper API만 로컬 fixture를 사용했다. iOS 시뮬레이터·Android 에뮬레이터 첫 제출 6/6건에서 화면에 표시된 이름·가격·대표 이미지가 일치했다. Android에서 세 링크를 따로 재실행해 전체 상품명과 가격을 검사한 결과도 3/3건 일치했다. iOS의 긴 이름 끝은 캡처에서 검증하지 못했다.

## 외화 표시와 통화 없는 JSON-LD 가격 구분

상품 페이지의 가격 통화 태그나 동일 상품의 제안 목록에 외화 표시가 있으면, 같은 상품이라도 통화가 없는 JSON-LD 금액을 원화로 해석하지 않는다. 명시적으로 원화라고 표시한 제안이 있고 유효한 원화 가격이 하나면 그 값을 사용할 수 있다. 외화 표시가 전혀 없는 기존 한국어 페이지의 통화 없는 가격 처리와 상품 ID 검증은 유지한다.

보관한 지그재그 `169420901`·`171067691`의 원본 구조화 데이터를 재생했을 때 결과는 동일했다. USD 통화 태그와 통화 없는 금액 `29`를 넣은 변형 2건은 변경 전 29원으로 해석됐고, 수정 후 가격은 비었다. 같은 변형에 명시적 KRW 제안도 넣은 2건은 원래 원화 가격으로 복구했다. 실제 쇼핑몰에서 해당 외화 조합을 관찰한 것은 아니다.

일반 규칙으로 무신사 `442429`(57,000원), 에이블리 앱 주소 `13848135`(11,340원), 지그재그 제휴 `169420901`(35,690원)을 실서비스 쇼핑몰에 요청했다. 로컬 Ziper API를 연결한 iOS 시뮬레이터·Android 에뮬레이터의 첫 제출 6/6건에서 화면 표시 이름·가격·대표 이미지가 앞서 확인한 상품과 일치했다. 별도 Android 재실행에서 전체 상품명·가격도 3/3건 일치했다. iOS에서는 긴 이름 전체를 검증하지 못했다.

## 공유 제목보다 상품 상세 이름 우선

처음 검증하는 상품 6개를 별도 Android Chrome에서 열어 상세 상품명·가격·첫 이미지를 확인했다. 앱의 첫 제출 12/12건에서 자동 입력됐지만 Android의 전체 제목 비교에서는 지그재그·무신사 각 2건에 판매처·브랜드 접두사가 붙었다. 자동 입력 안내만으로 정확도를 판단할 수 없는 사례다.

지그재그 `getPdpBaseInfo`와 무신사 `Detail`에서 요청 상품이 확인되면, 판매처가 붙는 공유 제목 대신 상세 상품명을 쓴다. 무신사는 상세 기록이 없어도 SKU가 일치하고 기재된 상품·제안 주소가 충돌하지 않는 JSON-LD의 이름을 우선한다. HTML의 공유 카드가 상세 데이터보다 먼저 수신되는 것도 지그재그 `123966326`에서 확인했다. 문서가 아직 파싱 중이면 공유 제목만 최대 600ms 보류한다. 상세 데이터가 없으면 그대로 공유 제목을 쓰며 로딩 시간 한도나 쇼핑몰 요청 횟수는 늘리지 않는다. 자동 테스트는 다른 상품 ID를 거부하고, 상세 데이터가 늦게 도착하거나 끝까지 없을 때의 결과를 각각 확인한다.

무신사 `4409450`의 구매 영역에는 93,370원이 표시됐지만 최저가 도전 안내에 상품·장바구니 쿠폰을 적용했고 보유 쿠폰에 따라 실제 구매가가 다르다고 명시돼 있었다. 따라서 공개 판매가 96,990원을 유지했다. 에이블리 `4609233`은 GIF의 다른 프레임 때문에 캡처가 달라 보였지만 Chrome 첫 이미지와 Android 등록 화면의 실제 이미지 URL이 일치했다.

Android 재검증에서는 에이블리 `4947701`(16,900원)·`4609233`(17,480원), 지그재그 `131486027`(23,400원)·`123966326`(15,920원), 무신사 `288168`(358,000원)·`4409450`(96,990원) 6건의 이름 전체와 가격을 브라우저 기준과 대조했다. 6/6 일치했고 대표 이미지도 확인했다. 상세 기록만 우선한 중간 버전에서 Android 무신사 2건에 접두사가 남았으며, 동일 상품 JSON-LD 보완 후 재제출에서 해결됐다. iOS 시뮬레이터에서도 같은 6건의 표시 이름·가격·대표 이미지를 확인했다. 긴 이름 전체는 캡처로 검증하지 못했다. 중간 실행에서 iOS `123966326`이 빈 폼으로 끝난 기록은 별개다. 다음 실행에서 성공했지만 그 원인이 해결됐다고 단정하지 않는다. 별도 무신사 OneLink `4804589` Android 재제출은 24,490원과 이름·이미지가 맞았으나 앞서 관측한 간헐 실패의 원인이 해결됐다는 뜻은 아니다. ## 대표 이미지 경로의 상품 번호 확인

실제 무신사 `4523101`의 상세 이미지 CDN 경로 `images/prd_img/<날짜>/<상품번호>/…`와 지그재그 `137794146`·`123966326`의 CDN 경로 `original/c/…/<상품번호>-<이미지번호>.…`에서 상품 번호를 확인했다. 이제 허용된 CDN이라도 이 형식의 경로가 다른 상품을 가리키면 제외한다. 다른 상품 번호로 바꾼 공유 이미지가 정상 이미지 후보보다 앞에 오는 상황을 재생했다. 변경 전에는 그 경로를 선택했고, 변경 후에는 같은 상품의 상세 이미지가 있으면 사용하고 없으면 이미지를 비워 뒀다. 실제 쇼핑몰에서 잘못된 번호를 반환한 사례는 아니다. 지그재그 날짜 기반 이미지 등 상품 번호가 없는 기존 경로는 그대로 허용한다.

별도 임시 로그에서 무신사 OneLink `4804589`와 `6623590`을 다시 추적했다. Android `4804589`의 한 시도에서 메타데이터가 주소 보고보다 4ms 먼저 도착했고, 앞서 넣은 대기 처리가 이를 받아 정상 결과를 반환했다. 동일 OneLink의 과거 빈 폼은 재현되지 않았다. 추적 중 수정이 적용된 iOS 지그재그 제휴 실행 1건은 상품 도착 뒤 Metro 새로고침과 겹쳐 빈 폼으로 끝났으므로 일반 실행과 분리했다. 임시 로그는 최종 코드에 포함하지 않았다.

최종 코드로 지그재그 `137794146`(44,800원)·`130476889`(35,200원)·제휴 `169420901`(35,690원), 무신사 `4523101`(59,000원), 에이블리 `26826616`(21,600원)을 양쪽에서 다시 열었다. 제출한 10/10건의 화면 표시 이름·가격·대표 이미지가 기존 원본과 일치했다(실제 쇼핑몰, 로컬 Ziper API). iOS 제휴 링크는 전체 이름과 정규 주소도 확인했다. 이 결과는 선택된 링크의 회귀 결과이며 운영 성공률이 아니다.

## 에이블리 첫 상세 이미지로 복구

Android Chrome에서 에이블리 공개 상품 5개의 첫 대표 이미지 요소(`goods-detail-cover-item.0`)를 확인했다. 메타데이터에서 허용된 이미지 URL을 찾지 못하면, `product:retailer_item_id`가 요청 상품 번호와 일치할 때만 그 요소의 `currentSrc`를 사용한다. 상품 번호가 없거나 충돌하거나, 이미지가 허용된 HTTPS CDN이 아니면 사용하지 않는다. 두 번째 슬라이드나 추천 상품 이미지는 읽지 않는다. 기존 공유 카드에서 확인한 이미지는 그대로 우선하고, 카드 폼에서 실제로 로드되었는지도 계속 확인한다.

수집한 카드 태그와 원본 이미지 URL을 재생했을 때 정상 5건은 변경 전과 같았다. 이미지 태그만 제거한 변형 5건은 변경 전 이미지가 비었고 변경 후 원본 첫 컷을 복구했다. 상품 번호가 없거나 다른 번호로 바뀐 경우에는 복구하지 않았다. 이미지 태그가 없는 실제 응답을 관찰했다는 뜻은 아니다.

로컬 Ziper 규칙에서 에이블리 이미지 선택자만 비우고 실제 쇼핑몰의 직접 링크 `595218`(19,900원)·품절 `3602080`(7,900원), 앱 링크 `13848135`(11,340원), 단축 링크 `51978009`(74,900원)를 양쪽에서 제출했다(8/8). 전체 이름과 가격은 앱 입력값과 원본을 대조했다. Android는 로드된 이미지 URL을, iOS는 이미지 캡처를 원본 첫 컷과 대조했다. 일반 규칙의 별도 실행은 양쪽 10/10건에서 자동 입력됐고 Android 5/5건의 전체 이름·가격·이미지 URL이 원본과 일치했다. Android 무신사 OneLink·지그재그 제휴 링크 회귀 2/2건은 자동 입력됐고 에이블리 이벤트 주소는 빈 폼으로 끝났다. 강제로 폴백을 사용한 결과를 운영 성공률로 집계하지 않는다.

## 에이블리 공개 판매가를 상세 화면에서 복구

에이블리 실제 상세 페이지 4건에서 공개 가격은 `goods-detail-send`(공유하기)와 같은 줄의 첫 가격 묶음에 있었다. 이 묶음의 `원` 표시가 유일하고 금액 전체가 원화 정수로 해석될 때만 사용한다. `product:retailer_item_id`와 주소의 상품 번호가 같아야 하고, 메타데이터에 명시적인 외화 표시가 있으면 보류한다. 정가·적립금·개인별 예상 구매가·회원 가격은 이 묶음 밖이므로 사용하지 않는다. 기존 메타데이터 가격을 읽을 수 있으면 그대로 우선한다.

수집한 실제 가격 영역과 메타데이터 4건을 재생했다. 정상 결과는 그대로였고, 가격 태그만 제거하면 변경 전에는 금액이 비었지만 변경 후에는 19,900원·7,900원·11,340원·74,900원을 복구했다. 외화 표시, 주소와 다른 ID, 가격 묶음 내 여러 금액은 테스트에서 제외되는 것을 확인했다. 이는 실제 페이지 일부를 변형한 검증이지, 쇼핑몰에서 가격 태그가 빠진 응답을 관찰했다는 의미가 아니다.

로컬 Ziper 규칙에서 에이블리 가격 선택자만 비우고 같은 직접·앱·단축 링크를 양쪽에서 다시 제출했다. Android 4/4건은 정규 주소·전체 이름·가격·실제 로드된 이미지 URL이 원본과 일치했고, iOS 4/4건은 정규 주소·전체 이름·가격과 화면의 대표 컷이 일치했다. 별도 Android 무신사 OneLink·지그재그 제휴 링크는 2/2건 자동 입력됐으나 지그재그 `169420901`의 표시 이름에 판매처가 붙어 이 건은 정확도 성공에서 제외했다.

## 지그재그 상세 제목으로 판매처 접두사 보정

위 제휴 링크의 접두사 불일치와 별도로, 보관한 지그재그 `169420901`·`171067691` 페이지 둘 다 공유 제목에는 판매처가 붙고 상세 `h1`에는 실제 상품명만 있었다. 초기 상세 데이터만 뺀 재생에서 이전 버전은 판매처가 포함된 제목을 반환했다. 이제 상세 데이터에서 이름을 가져오지 못할 때, 주소·Open Graph 주소·`product:retailer_item_id`가 같은 상품을 가리키고 유일한 `h1`의 전체 문구가 공유 제목의 끝과 일치하면 그 제목을 사용한다. 상품 ID가 없거나 제목이 일치하지 않으면 기존 결과를 유지하고, 다른 ID가 표시되면 결과를 사용하지 않는다. 원본 2건은 변경 전과 같았으며 초기 데이터 제거 변형 2건에서는 원본 상품명을 복구했다. 과거 실응답에서 초기 데이터가 빠졌는지는 따로 확인되지 않았다.

일반 규칙으로 지그재그 제휴 `169420901`과 직접 `171067691`, 무신사 OneLink `4804589`, 에이블리 직접 `595218`을 다시 제출했다. iOS 시뮬레이터·Android 에뮬레이터 8/8건의 정규 주소·전체 상품명·공개 가격을 대조했고, 대표 이미지는 원본 화면과 비교했다. Android 무신사는 갤러리 DOM의 첫 노드가 아닌 화면의 첫 슬라이드와 같은 컷임을 확인했다. Ziper API는 로컬 fixture이고, 이 재제출은 앞선 상품명 불일치 건과 별도다.

## 지그재그 상세·구형 가격의 통화 확인

외화가 표시된 페이지에서 통화 없는 JSON-LD 가격을 제외하더라도, 지그재그 구형 `final_price` 또는 상세 데이터의 `final_discount_info`가 같은 금액을 원화로 채울 수 있었다. 페이지 가격 태그나 동일 상품 제안에 외화 표시가 있으면 두 경로의 통화 없는 금액을 제외한다. 상세 화면용 가격이 원화로 명시되어 있으면 그 금액은 사용하고, 기존 원화 전용 상품의 결과는 유지한다.

보관한 지그재그 `169420901`·`171067691`의 정상 가격 35,690원·103,200원은 그대로였다. USD 메타 태그와 통화 없는 `29`를 주입한 각 변형은 이전 코드에서 29원으로 읽혔다. 수정 후에는 원화 표기가 없는 변형의 가격이 비었고, 원화로 표시된 상세 가격이 있는 변형은 공개 가격을 복구했다. 실제 쇼핑몰에서 외화 혼입 응답을 받은 것은 아니다.

별도로 이전에 검사하지 않은 상품 6개를 Android Chrome에서 열어 원본을 확보했다. 에이블리 `12238610`(28,400원)·`3223127`(5,600원), 지그재그 `128325389`(26,170원)·`135483198`(16,290원), 무신사 `1621266`(189,000원)·`541326`(139,000원)이다. 두 플랫폼 첫 제출 12/12건의 정규 주소·전체 이름·가격을 원본과 대조했다. 대표 컷은 Android에서 실제 로드된 URL, iOS에서 캡처를 사용했다. 지그재그 `128325389`의 브라우저 응답에는 가격 메타 태그와 상품 JSON-LD가 없었지만 정상 가격을 얻었다. 에이블리 `3223127`에서 로딩 도중 실제로 `0원`이 표시됐으나 이때 상품 번호와 대표 컷은 없었다. 상품 번호 검증 후 5,600원이 들어갔으며, 유효한 상품의 실제 0원은 차단하지 않는다. ## 판매 종료 에이블리 알림이 수동 입력을 가리지 않도록 처리

새 상품 표본을 선정하다 에이블리 `4121330`을 확인했다. 정상 브라우저에서 `판매 중인 상품이 아닙니다` 알림이 나왔고, Android 앱에서도 숨은 WebView의 같은 알림이 Ziper 등록 화면을 가렸다. URL 확인은 끝났지만 앱 자동화는 32초 안에 등록 화면의 완료 상태를 관측하지 못했다. 판매 종료 주소이므로 유효 상품의 정확도 분모와는 별도로 기록했다.

에이블리 상품을 읽는 숨은 WebView 안에서만 해당 안내 문구의 `alert`를 띄우지 않고 그 문서의 스캔을 종료한다. 정상 메타데이터로 취급하지 않고 수동 입력으로 넘어간다. 기타 알림과 접근 제한 처리는 변경하지 않았다. 자동 테스트는 이 문구 이후 상품처럼 보이는 태그가 추가되어도 보내지 않는지, 다른 문구는 원래 `alert`에 전달되는지 검증한다. 같은 판매 종료 주소를 다시 제출했을 때 iOS 시뮬레이터와 Android 에뮬레이터에서 상품 이미지가 없는 수동 폼에 도달했다.

별도로 이번에 처음 본 유효 상품 5개를 원본과 대조했다. 지그재그 추적 링크 `135355746`(20,900원)·`143396857`(16,900원), 무신사 `112779`(165,000원)·`346929`(159,800원), 에이블리 `4966147`(61,650원)이다. 첫 제출 10/10건의 정규 주소·전체 이름·공개 가격이 맞았고, Android는 실제 로드한 이미지 URL, iOS는 화면의 대표 컷을 비교했다. 쇼핑몰은 실제 요청, Ziper API는 로컬 fixture였다. 수정본에서 상점별 1개씩 다시 제출한 6/6건도 동일했다. Android에서 판매 종료 주소를 한 번 더 제출해 정규 주소를 유지하면서 이름·가격·이미지가 모두 비었음을 폼에서 직접 확인했다.

## 구조화 데이터의 상품 주소도 대조

무신사 공개 페이지 `4409450`·`4804589`의 JSON-LD `Product`는 `sku`·`url`뿐 아니라 `@id`에도 해당 상품 주소를 담고 있었다. 이제 허용된 HTTPS 호스트와 상품 경로의 `@id`도 상품 번호로 대조한다. 다른 상품을 가리키면 그 구조화 노드를 제외하고, `sku`나 `url`이 없더라도 해당 상품을 확인하는 주소가 남아 있으면 읽을 수 있다. `#product`처럼 상품 번호를 확인할 수 없는 식별자는 증거로 취급하지 않는다. 상품·제안 주소 검증은 그대로 유지한다.

두 페이지에서 수집한 원본 JSON-LD의 결과는 변경 전과 같았다. `@id`만 남기고 다른 상품 노드를 추가한 변형 2건은 이전에 결과를 보내지 못했지만 수정 후 전체 이름·공개 가격·이미지를 복구했다. `@id`를 다른 상품 주소로만 바꾼 2건은 수정 후 제외됐다. 이 변형은 구조화 데이터의 변동과 충돌을 재현한 것이며, 실제 쇼핑몰에서 두 조건을 받은 것은 아니다.

일반 규칙으로 무신사 직접 `4409450`·`112779` 및 OneLink `4804589`, 지그재그 추적 `135355746`, 에이블리 직접 `4966147`을 iOS·Android에 제출했다. 10/10건의 정규 URL·전체 상품명·공개 가격이 맞았고, Android 이미지 URL과 iOS 대표 컷을 브라우저 기준과 대조했다. 쇼핑몰은 실제 요청, Ziper API는 로컬 fixture였다.

## 무신사 요약이 없어도 상품 번호가 일치하는 상세 데이터 사용

무신사 `4409450`·`4804589`의 공개 상세 데이터에서 `Detail` 쿼리와 레코드의 `goodsNo`가 주소의 상품 번호와 일치했고, 레코드 안에 상품명·판매가·대표 이미지가 있었다. 기존에는 별도 요약의 상품명이 일치해야만 상세 데이터를 사용했다. 이제 요약이 없거나 다른 이름이면 요약을 제외하고 상품 번호가 일치하는 상세 레코드에서 읽는다. 원화 통화와 쿠폰 적용 전 공개 판매가 조건은 유지한다.

수집한 원본은 이전과 동일했고, 요약을 제거하거나 다른 상품의 1원·이미지를 넣은 재생 4건은 이전에 빈 결과였으나 수정 후 두 상품의 전체 이름·가격·대표 이미지를 복구했다. 다른 `goodsNo`는 거부했고, 상세 레코드에 USD를 표시하면 가격은 비웠다. 실제 쇼핑몰에서 요약이 누락됐다는 뜻은 아니다. 일반 규칙으로 무신사 `4409450`, 지그재그 추적 `135355746`, 에이블리 `4966147`을 iOS 시뮬레이터와 Android 에뮬레이터에 제출한 6/6건에서도 전체 이름·가격·대표 이미지가 기존 원본과 일치했다. 쇼핑몰은 실제 요청, Ziper API는 로컬 fixture였다.

## 규칙 응답 본문이 끊길 때 복구

유효한 규칙 캐시가 없고 `200` 응답의 본문 읽기가 중단됐을 때만 규칙을 한 번 더 요청한다. 게이트웨이 오류와 재시도 한 번 및 2초 한도를 공유한다. 취소, 확인 가능한 `Retry-After`, 완전히 읽었지만 잘못된 JSON·스키마는 재시도하지 않는다. 유효한 캐시가 있으면 재요청 없이 쓰되 만료를 연장하지 않는다.

로컬 Ziper API에서 캐시를 비운 뒤 첫 규칙 본문의 연결을 종료하고 두 번째 본문을 정상 전송했다. 지그재그 추적 `135355746`, 에이블리 `4966147`, 무신사 직접 `112779`·`4409450` 및 OneLink `4804589`를 양쪽 OS에 제출했다. 읽기 오류 뒤 규칙 재요청과 정상 본문 수신은 10/10건에서 확인됐다. 실제 쇼핑몰 페이지까지 열어 정규 주소·전체 이름·가격·대표 이미지가 일치한 첫 제출은 iOS 5/5, Android 1/5였다. Android에서 실패한 무신사 3건과 에이블리 1건은 모두 규칙 다운로드에 성공했지만 수동 입력으로 전환됐다. 이 규칙 복구를 운영 장애 재현이나 쇼핑몰 추출 성공률로 해석하지 않는다.

Android 원인 확인용 별도 재실행에서 무신사 `112779`는 추출 WebView의 메인 페이지가 `403`을 반환해 재시도 없이 수동으로 전환됐다. 에이블리 `4966147`은 약 5.6초 후 정상 메타데이터가 도착해 정규 주소·이름·가격·이미지가 모두 맞았다. 에이블리 첫 실패와 나머지 무신사 실패의 원인은 확인되지 않았다. 재실행은 첫 제출 집계에 합치지 않고, 임시 계측은 제거했다.

무신사 `4409450`·`4804589`의 공개 상세에는 상품 요약과 상품 번호로 확인한 `Detail`에 각각 `salePrice`가 있었다. 요약의 가격 객체가 있어도 유효한 공개 원화 판매가가 없으면 같은 상품의 `Detail.salePrice`로 보완한다. `finalPrice`만 남아 있고 어느 쪽이든 쿠폰 적용을 표시하면 자동 입력하지 않는다. 외화 및 잘못된 상품 번호는 계속 제외하며, 정상 원화 0원은 유지한다.

## 쿠키 세션과 추출 규칙 조회 통합

최신 `main`의 HttpOnly 세션과 상품 PR의 요청 취소·업로드·ETag 지원을 통합했다. 세션 갱신은 쿠키 모드로 한 번 공유하며, 추출 규칙 요청의 2초 한도가 먼저 끝나도 다른 URL 확인 요청이 기다리는 쿠키 갱신을 취소하지 않는다. 앱의 규칙 조회와 URL 확인은 갱신된 액세스 토큰을 사용한다.

자동 테스트에서 4초 지연된 쿠키 갱신(본문·취소 신호 없음), 먼저 종료한 규칙 조회, 같은 갱신 결과를 받은 URL 확인을 검증했다. 개발 프록시의 쿠키·ETag·`Retry-After` 전달은 모의 응답으로 확인했다. 실제 운영 세션이나 계정으로 저장한 결과는 아니다.

HttpOnly 쿠키를 제공하는 로컬 Ziper API로 양쪽 OS에서 규칙 `401` → 쿠키 재발급 → 규칙 `200`/`304`를 확인했다. 쇼핑몰은 실제로 열었다. 정규 주소·전체 상품명·공개 가격·대표 이미지가 맞은 결과는 iOS 3/3(지그재그 `135858160`, 에이블리 `3798513`, 무신사 `338418`), Android 3/4(지그재그 `135858160`·`137389236`, 에이블리 `3798513`)였다. Android 무신사 `338418`은 규칙 재확인까지 성공했지만 수동으로 전환됐다. 원인은 확인하지 못했다. Android 딥링크로 입력 화면에 도달하지 못한 자동화 시도는 제출 집계에서 제외하고 홈의 ‘상품 추가’로 다시 실행했다. 브라우저에서는 로컬 URL 확인·쿠키 갱신·보드 조회 후 빈 입력 폼으로 이동했으며, 쇼핑몰 또는 추출 규칙 요청이 없었다.

## 로그인한 홈에서 추출하고 URL 끝 문장부호 처리

실제 쇼핑몰 E2E는 로그인 화면을 기다리는 공통 프리뷰 절차 대신, 쿠키 세션이 복원된 홈에서 ‘상품 추가’로 진입한다. 로컬 Ziper API와 실제 상품 페이지로 옮긴 첫 제출 기준 iOS 3/3, Android 3/4였다. 실패한 Android 무신사 `338418`은 규칙 `304` 이후 메인 페이지가 `403`을 반환했다. 파서에 상품 데이터가 도착하지 않았고 재시도 없이 수동으로 전환됐다. 이전 계측 없는 실패까지 모두 `403`이었다는 뜻은 아니다.

단독으로 붙여넣은 URL의 맨 끝에 문장부호가 붙으면, 원래 주소가 상품 주소로 인식되지 않고 문장부호를 제거한 결과가 알려진 상품 주소일 때만 보정한다. 유효한 상품 쿼리, 단독 단축 링크, 다른 사이트 주소는 그대로 둔다. 문장부호를 붙인 별도 실험에서는 iOS 지그재그 `135858160`·에이블리 `3798513`·무신사 `338418`과 Android 지그재그·에이블리(같은 상품) 5/5건의 정규 주소·전체 이름·공개 가격·대표 이미지가 맞았다. Android 무신사는 이 5건에 포함하지 않았다. 이 실험은 운영 성공률을 나타내지 않는다.

## 지그재그 구형 금액보다 원화 화면 표시가 우선

최종 코드에서 로컬 Ziper API가 최초 규칙 응답에 잘못된 헤더를 보내게 한 7/7건에 후속 정상 규칙이 도착했다. 상품 번호 태그가 아직 없더라도, 모든 OG 카드 주소가 요청 상품을 가리키고 공유 버튼과 같은 상세 영역에서 찾은 유일한 제목이 카드 제목과 일치할 때만 해당 영역의 가격과 첫 상세 커버를 읽는다. 상품 번호가 다르거나 카드가 서로 다른 상품을 가리키거나 제목이 다르면 이 경로를 쓰지 않는다. 외화가 명시되면 가격을 채우지 않는다. 대기 시간이나 네트워크 요청은 늘리지 않았다.

Daum에서 새로 찾은 에이블리 `14929801`의 Chrome 상세에서 이름·14,800원·첫 이미지 URL을 확인했다. 수정 후 실제 쇼핑몰 첫 실행은 제출이 확인된 Android 1건과 iOS 3건 모두 수동 입력으로 전환됐다. Android 3건의 입력·실행 실패와 iOS 1건의 입력 화면 실패는 제출 전에 발생했다. 별도 직렬 재실행에서는 iOS 3/3 정확(에이블리 `14929801`, 지그재그 `114542806`, 무신사 `2027860`), Android 1/3 정확(에이블리 `14929801`)이었다. Android 지그재그·무신사는 재실행에도 수동으로 전환됐다. 양쪽 에이블리 재실행에서 정규 주소·전체 이름·14,800원·대표 이미지를 확인했다. 첫 제출과 재실행은 합치지 않는다. Ziper API는 로컬 fixture였으며, 수동 전환의 원인은 확정하지 못했다.

## URL 확인 응답 중단과 쇼핑몰 실패 구분

같은 네 상품의 첫 제출에서 [iOS 시뮬레이터는 4/4](https://github.com/user-attachments/assets/9c216828-f9e2-4e1b-8d59-3282e08f8550), Android 에뮬레이터는 1/4가 정확했다(실제 쇼핑몰, 로컬 Ziper API). Android 지그재그 `114542806`은 정확했고, 무신사 `2027860`은 메인 프레임에서 약 1.58초 만에 `403`을 받아 수동 입력으로 전환됐다. 에이블리 `14929801`은 탐색 콜백 없이, `10518347`은 약 6.60초에 상품 탐색 콜백을 받은 뒤 로드 완료·메타데이터 없이 8초에 종료됐다. 네 건 모두 Ziper의 규칙과 URL 확인 단계를 통과했다. 이 실패는 URL 확인 재시도로 해결되는 문제가 아니다.

별도 장애 실험에서는 **Ziper의 읽기 전용 URL 확인**만 끊었다. 지그재그는 잘못된 응답 헤더, 무신사는 `200` 본문 전송 중 연결 종료를 사용했다. 두 OS 모두 같은 주소로 한 번 더 확인해 4/4건에서 전체 필드와 대표 이미지를 표시했다([Android 첫 제출과 장애 실험 비교](https://github.com/user-attachments/assets/d334e02d-00a6-4c29-bb10-4f81889935b8)). 기존 게이트웨이 복구와 한 번의 재시도·5초 제한을 공유한다. 취소, 거부, 속도 제한, 읽을 수 있는 `Retry-After`, 끝까지 수신한 잘못된 `200`은 재시도하지 않는다. 상품 등록이나 쇼핑몰 요청을 반복하지 않는다.

Android WebView는 방문 기록에 문서를 추가할 때 `onLoadStart`를 보낸다. 직접 에이블리 링크에서 5~8초 사이에 같은 HTTPS 상품의 방문 기록을 확인하면 이제 로드 완료 전이라도 기존 12초 상한을 사용할 수 있다. 진행률이나 최초 요청만으로는 연장하지 않는다. iOS와 다른 쇼핑몰, 재시도 횟수는 그대로다. [별도 Android 재실행](https://github.com/user-attachments/assets/799f1d88-3910-48e9-8b15-c66ed0cac718)에서 `10518347`은 6.55초에 방문 기록이 도착했고 11.24초에 전체 이름·98,000원·검증된 첫 이미지가 일치했다. `14929801`은 방문 기록 없이 다시 8초에 종료됐다. 두 건을 합치면 1/2다.

진단 코드를 제거한 뒤 에이블리 `10518347`, 지그재그 `114542806`, 무신사 `2027860`을 [양 OS에서 별도로 재검증](https://github.com/user-attachments/assets/fa8dde5b-9ff8-4a65-97dc-79b7168e5e61)했다. 이번 6/6건은 원래의 대표 이미지와 정규 주소·전체 이름·공개 가격이 일치했다. `14929801`은 이 재검증에 포함되지 않았다. 자동 테스트 510개, 코드 검사, 앱·웹 타입 검사 및 웹 빌드를 통과했다.

Daum 검색에서 에이블리 우산 링크 4개와 무신사 링크 1개를 찾았다. 에이블리 `10262821`은 데스크톱에서 확인 화면, 무신사 `1977091`은 접근 거절 화면을 반환해 독립적인 필드 비교에서는 제외했다. `10262821`을 독립 웹에 입력했을 때 가격·이름은 비어 있었고, 세션·URL 확인·보드 조회 외에 쇼핑몰이나 규칙으로 가는 요청은 없었다.

## 추천 링크의 가격과 지그재그 종료 상품 구별

모바일 Chrome에서 에이블리 우산 `10262821`(9,800원), 지그재그 운동화 `131644910`(17,580원), 무신사 슬리퍼 `1004681`(9,900원)의 전체 이름·공개 가격·첫 이미지를 대조했다. 로컬 Ziper API와 실제 쇼핑몰을 사용했다. 이전에 Android에서 시간 초과된 에이블리 `14929801`까지 포함한 이번 첫 제출은 iOS 4/4, Android는 제출 확인 3/3 정확했다. Android 지그재그 한 건은 제출 전 URL 입력 검사를 통과하지 못했고 별도 재실행에서 정확했다. 에이블리 타임아웃 원인 해소를 뜻하지 않는다.

추천 상품의 `url: "?ref=recommend"`, `offers.url: "#offer"`가 현재 문서 경로를 상속해 그 상품의 식별자로 오인될 수 있었다. 경로 없는 참조만으로는 상품을 식별하지 않는다. 실제 상품 ID나 상품 경로가 따로 있으면 같은 문서 내부의 `#offer`는 허용한다. 정상 수집본은 그대로였고, 가격 태그를 없애고 1원짜리 추천 항목을 넣은 재생에서는 4/4건 모두 1원 대신 원래 가격을 읽었다. 이는 실제 판매처가 1원을 표시했다는 뜻이 아니다. 수정 후 [세 쇼핑몰 별도 재검증](https://github.com/user-attachments/assets/c781c729-80e9-4bca-bebe-2df6c0c41d83)은 두 OS 각 3/3 정확했다.

지그재그 `143403793`은 모바일 Chrome에서 **존재하지 않는 상품**인데 같은 ID의 `getPdpBaseInfo`에 이름·28,000원·이미지가 남아 있었다. 두 OS에서 잘못 자동 입력되는 것을 재현했다. 같은 판매처의 `143403748`·`143403746`도 같은 안내와 `sales_status: CLOSED`인 상세 데이터를 함께 내줬다. 이제 `CLOSED`인 기록은 현재 상품 상세의 유일한 `h1`이 상품명과 맞을 때만 사용한다. 조회 횟수·대기 시간은 바뀌지 않는다. 원본 재생에서 종료 3건의 과거 가격(28,000원·24,800원·24,800원)을 모두 제외했고, 페이지를 실제 볼 수 있는 품절·판매 중지·판매 중 7건은 유지했다. [양 OS의 수정 전·후 화면](https://github.com/user-attachments/assets/167d9ca7-ee5f-4f3e-a8ad-afe0100987e8)에서 `143403793`이 빈 수동 입력으로 바뀌었다. 없는 상품은 유효 링크 성공률에 넣지 않았다. 별도 정상 할인 상품 `135339211`은 양 OS 모두 정가 10,500원이 아닌 공개가 9,450원과 전체 이름·대표 이미지가 맞았다.

종료 상품 수정 뒤에도 [세 쇼핑몰의 정상 상품 재검증](https://github.com/user-attachments/assets/0cc7673b-16eb-4b32-8a87-a3757ae0eb75)은 양 OS 각 3/3 정확했다. 추출 조건을 바꾼 후 같은 상품을 다시 본 결과이지 신규 독립 표본은 아니다. 에이블리 `4382632`와 무신사 `1977091`은 브라우저에서 DNS 오류가 발생했고, 무신사 재확인은 캠페인 화면으로 이동해 상품 원본을 확인하지 못했다. 이 둘은 앱에 제출하지 않았고 분모에 넣지 않았다. 자동 테스트 510개·코드 검사·앱/웹 타입 검사·웹 빌드 통과. 운영 `/readyz`와 `/livez`는 연결 리셋으로 확인하지 못했고 연결된 모바일 실기기는 없었다.

## 새 상품 첫 제출과 저장 공간 부족 시 규칙 재사용

Daum 검색으로 찾은 에이블리 귀걸이 `16106967`·`1853996`, 지그재그 지갑 `134446388`·`119606435`, 무신사 지갑 `302515`·`265117`을 모바일 Chrome 원본과 대조했다. [수정 전 첫 제출](https://github.com/user-attachments/assets/a6932140-d256-41ec-a243-368c870d63de)은 iOS 시뮬레이터 6/6, Android 에뮬레이터 6/6에서 정규 주소·전체 상품명·공개 가격·대표 이미지가 맞았다. 무신사 `302515`는 정가 79,400원이 아닌 판매가 63,520원이었다. Android에서 이 상품의 스크린샷은 이미지가 로드되기 전 찍혔지만, 같은 제출의 최종 폼에서 원본 대표 컷과 같은 URL 경로·로드 완료·이미지 너비를 확인했다. 실제 쇼핑몰과 로컬 Ziper API를 사용했고 재시도는 없었다.

별도 Chromium 실험에서 테스트 출처의 저장 공간을 채워 `QuotaExceededError`를 재현했다. 규칙 `200` 뒤 저장에 실패하면 `getItem`은 예외 없이 빈 값을 반환했다. 다음 제출에서 규칙 서버가 `503`을 주면 이전 코드는 유효한 메모리 규칙을 무시해 추출 호출을 건너뛰었다. 이제 쓰기나 삭제에 실패한 동안에는 **같은 페이지 메모리**의 마지막 검증 결과를 사용한다. 저장소 쓰기가 성공하면 영속 저장소를 다시 사용한다. 기존 5분 한도는 연장하지 않으며 `403` 후 삭제가 실패해도 같은 페이지에서 과거 규칙을 되살리지 않는다. 저장에 실패한 규칙이 앱 재시작 후에도 남는다는 뜻은 아니다.

Chromium에서 두 번째 호출이 복구됐고, [양 OS의 별도 앱 장애 실험](https://github.com/user-attachments/assets/5c7bf083-3d6d-4279-9a3e-a5a602926dac)에서도 규칙 저장 실패를 주입한 뒤 같은 폼으로 돌아가 다른 링크를 제출했다. `503`과 `Retry-After`에서 규칙을 재요청하지 않고 iOS는 무신사 63,520원, Android는 지그재그 10,800원과 전체 이름·대표 이미지를 표시했다. Android도 로컬 디버깅 포트 없이 `e2e/live/assert-product-fields.mjs`로 전체 입력값을 대조할 수 있다. 두 OS의 실제 스냅샷으로 검증했고 줄인 상품명은 실패했다.

수정 후 세 쇼핑몰에서 [다른 상품 3개를 첫 제출](https://github.com/user-attachments/assets/50ee9db1-d5fa-4ed7-b128-ae53a442ad25)한 결과도 양 OS 각 3/3 정확했다. 에이블리 `1672707`은 정가 9,800원이 아닌 공개 행사 가격 3,920원, 지그재그 `123489260`은 8,500원, 무신사 `302521`은 선택 색상이 품절이어도 상세 화면의 59,520원과 대표 컷을 확인했다. 독립 웹에 `1672707`을 제출하면 상품명과 가격은 비어 있었고 규칙·쇼핑몰 요청은 없었다. 자동 테스트 513개, 코드 검사, 앱·웹 타입 검사 및 웹 빌드 통과. 운영 API 연결 리셋과 실기기 미연결로 운영 환경의 첫 제출 성공률은 확인하지 못했다.

## 쇼핑몰 공유 버튼으로 복사한 링크

일반 Android Chrome에서 에이블리 `1672707`의 공유 버튼은 `https://applink.a-bly.com/8uwnjcs`를 복사했다. 무신사 `302515`의 OS 공유 창과 지그재그 `119606435`의 ‘링크 복사하기’는 각각 정규 상품 주소를 내줬다. 세 상품 자체는 이전에 검증했지만 에이블리의 이번 **단축 주소 첫 제출**은 iOS 성공, Android 수동 전환이었다. 수정 전 Android 재실행도 같은 상품의 마지막 방문 기록이 7.56초에 왔는데 8.01초에 빈 결과로 종료했다. 직접 주소 대조군은 5.65초에 읽혔다.

이제 단축 주소라도 **확인된 동일 에이블리 상품**이 늦게 로드되면 직접 주소처럼 시작 후 최대 12초까지 데이터 도착을 기다린다. 상품 미확인 상태의 대기나 오류 재요청 가능 시간은 늘리지 않는다. [같은 단축 주소 재실행](https://github.com/user-attachments/assets/49a68ef4-0df6-4db2-aeb0-13fb0fd39282)에서 Android는 재요청 없이 9.11초, iOS는 5.78초에 전체 메타데이터를 받았다. 그 전에 링크 입력·화면 열기에 실패한 각 OS 1건은 제출 전 도구 실패로 분리했다.

진단 코드 제거 후 [세 공유 주소](https://github.com/user-attachments/assets/7546aadb-d68d-4b46-92c2-684caa91d270)를 제출해 양 OS 각 3/3에서 주소·전체 상품명·공개 가격(3,920원·63,520원·10,800원)과 대표 컷을 확인했다. 실제 쇼핑몰·로컬 API의 같은 상품 회귀 검증이지 신규 상품 6건이 아니다. 자동 테스트 519개, 코드 검사, 앱·웹 타입 검사, 웹 빌드 통과. 운영 `/readyz`는 여전히 연결 리셋이었다.

## 신규 상품 7개와 겹친 규칙 요청

[신규 상품 첫 제출](https://github.com/user-attachments/assets/f4d9992e-b5c4-4205-b46e-90051662d2f5)은 iOS 시뮬레이터·Android 에뮬레이터 각각 7/7에서 정규 주소·전체 상품명·공개 가격·대표 컷이 맞았다. ## 같은 상품의 링크별 공개 표시가

에이블리 텀블러 `5462175`는 [일반 모바일 Chrome 원본](https://github.com/user-attachments/assets/3331ddd1-6291-44f5-90d0-7d740ea7d34f)에서 직접 주소로 열면 **25,000원**, 검색에서 찾은 `coupon_sno=44495066` 포함 주소로 열면 **22,500원**이었다. 추적 파라미터 없이 `coupon_sno`만 남겨도 같았다. 두 페이지 모두 상세 가격과 `product:price:amount`가 일치했다. 이는 링크에 공개된 표시가이지 로그인한 구매자의 결제 확정가가 아니다.

수정 후 새 상품 [세 건의 첫 제출](https://github.com/user-attachments/assets/f106c1c2-e364-4093-8375-32917180e88f)은 iOS 붙여넣기와 Android OS 공유 각각 3/3 정확했다. 에이블리 `9985242` 25,140원, 품절 지그재그 `145302216` 15,120원, 무신사 `748991` 69,000원. 독립 모바일 Chrome에서 제출 링크의 공개가·이름·대표 컷을 확인했다. 앞선 에이블리 `12756683`은 양 OS 모두 로딩 중의 0원이 아닌 35,620원을 읽었다. Android 지그재그 붙여넣기는 제출 전 입력 확인 단계에서 중단됐고, 앞서 실패한 무신사 문장부호 공유 재검증은 새 상품 수에 넣지 않았다. 판매 종료 에이블리 `4382632`에서 잠시 보인 0원·이전 상품 정보를 양 OS 모두 채우지 않은 것도 별도 음성 대조다.

## 지그재그 공개 시작가(`원~`)와 Android 공유 시 거절

[모바일 Chrome 원본과 수정 전후의 폼](https://github.com/user-attachments/assets/099ed6ab-fa2f-45b2-b762-fe5550f3731f). 지그재그 `131188742`는 9,900원~, `100214629`는 정가 188,000원과 쿠폰할인가 178,600원~을 표시했다. 두 상품 모두 같은 ID의 `display_final_price`가 `원~` 단위를 사용했고 `final_discount_info.discount_price`, `product:price:amount`, JSON-LD `Offer.price`가 같은 금액이었다. 이는 공개 **시작가**이며 선택한 옵션이나 개인의 최종 결제가는 아니다.

## 에이블리 앱 주소의 행사 가격과 무신사 제휴 경로

`https://a-bly.com/app/goods/{id}?coupon_sno=…`는 앱용 공유 주소이지만 모바일 Chrome에서는 같은 번호의 모바일 상세 페이지로 리다이렉트되면서 쿠폰이 적용됐다. `5462175`는 22,500원(일반 링크 25,000원), `427026`은 5,220원(일반 링크 5,800원)이었다. 변경 전 iOS와 Android는 두 링크 모두 **정상 자동 입력으로 표시하면서 일반 가격을 저장 폼에 넣었다**. 매번 쿠폰 여부를 추론하거나 다른 호스트에 임의의 쿼리를 복사하는 대신, 쿼리가 있는 이 경로만 원래의 HTTPS 주소에서 열어 쇼핑몰의 이동을 따른다. 중간 앱 주소는 가격의 출처로 쓰지 않고 재시도나 대기 연장 대상에서도 제외한다. 상품 ID는 이동 전부터 고정한다. 쿼리가 없는 앱 주소의 단축 처리와 저장용 정규 URL은 그대로다.

[같은 링크·두 OS의 변경 전후](https://github.com/user-attachments/assets/d2d7d941-f179-4af5-9f1f-43c602a52a6a): 두 상품의 전체 이름·행사 가격·첫 사진을 확인했다. Android `427026`은 첫 수정 후 붙여넣기 자동화가 링크 제출 전에 멈췄고 이후 OS 공유에서 정확했다. 이 2개는 기존 상품의 링크 변형이지 새 상품 2개가 아니다.

[새 상품 3개의 최초 제출](https://github.com/user-attachments/assets/1fb3b4dd-d763-4be0-a34d-fced9954d405): iOS 3/3, Android 2/3. 에이블리 `7619629`는 지난번 DNS 실패 때 제출하지 않았던 상품이다. 이번에는 추적 쿼리와 쿠폰이 함께 있는 앱 주소에서 화면·가격 메타 모두 11,610원으로 확인됐고 양 OS가 전체 이름·첫 사진·가격을 정확히 채웠다. 지그재그 `136938836`도 양 OS에서 16,500원으로 일치했다. 품절이지만 읽을 수 있는 무신사 `261105`는 iOS에서 105,000원과 첫 사진이 맞았고 Android는 빈 수동 폼이었다. **이 상품에서 HTTP 상태를 측정하지 않았으므로 403으로 단정하지 않는다.** 찾을 수 없는 에이블리 `15082715`는 별도 Android 음성 대조에서 이름·가격·이미지가 비었다. 독립 웹에서 앱 주소를 제출하면 수동 폼만 열리고 쇼핑몰 요청은 없었다. 로컬 Ziper API 기준이며 테스트 549개, 코드·타입 검사와 웹 빌드 통과.

무신사 거절에 대해서는 [회사 공식 사이트](https://corp.musinsa.com/) 하단의 [광고/제휴 문의](https://www.musinsa.com/app/company/partner?type=2)를 확인했다. 이동 후 **광고/제휴 문의** 탭은 사업 제휴 문의와 회사·담당자 정보 제출을 안내한다. 별도의 입점 문의는 판매자용이다. 이 안내는 Ziper가 임의 상품 ID로 구매자용 현재 가격·대표 사진을 조회할 수 있다는 계약이나 공개 API가 아니다. 실기기에서도 거절이 반복된다면 제휴 담당자가 대상 상품 범위, 행사 링크별 원화 가격, 이미지 재사용 권한, 갱신 주기와 요청 한도를 확인해야 한다. 문의를 제출하거나 비공개 API를 호출하지 않았고 서버 크롤링·거절 우회는 추가하지 않았다.

## 에이블리 기본 도메인의 행사 링크와 구조화 가격의 적용 범위

**실제 링크 오류.** `/app/goods/`가 아닌 `a-bly.com/goods/`도 에이블리 모바일 상세로 리다이렉트한다. 모바일 Chrome에 `https://a-bly.com/goods/%35462175?coupon_sno=44495066`와 `http://a-bly.com/goods/427026?coupon_sno=44081681`을 각각 입력해 같은 탭의 최종 주소와 공개 가격을 확인했다. 에이블리는 쿼리를 유지했고 화면과 가격 태그가 각각 22,500원·5,220원이었다. 반면 앱은 인코딩된 경로 또는 HTTP를 정리하면서 기본 도메인을 모바일 도메인으로 바꾸고 쿼리를 버렸다. 양 OS 모두 일반 가격(25,000원·5,800원)을 자동 입력했다. 이제 인식된 에이블리 상품 주소는 **제출한 호스트에서** HTTPS와 숫자 경로만 정규화하고 실제 이동은 쇼핑몰에 맡긴다. 무신사 등 다른 호스트로 쿼리를 복사하지 않고 저장용 정규 주소에도 붙이지 않는다. [Chrome 기준·Android 전후·iOS 전후](https://github.com/user-attachments/assets/d284e76d-6b2c-40e6-95bb-68c9843849d6): 두 링크 모두 수정 후 양 OS에서 전체 이름·행사 가격·첫 사진이 맞았다. `www.a-bly.com`에 같은 인코딩 주소를 사용한 별도 재시험도 Chrome과 양 OS에서 22,500원이었다.

**별도 캡처 변형 실험.** 같은 두 상품의 기본/쿠폰 주소 4개에서 읽은 원본에는 JSON-LD 상품이 없었다. 원본 그대로 재생하면 변경 전후 4/4 가격이 같았다. 가격 메타 태그만 빼고 같은 ID의 _다른 행사_ `Offer`를 추가하면 기존 코드는 4/4에서 그 금액을 현재 링크 가격으로 채웠다. 에이블리의 `ldjson:offers.price`는 이제 `coupon_sno`가 현재 문서와 일치하는 원화 금액만 사용한다. 링크에 쿠폰이 있으면 식별 근거 없는 일반 금액을 쓰지 않는다. Offer 주소가 없거나 `#offer`이면 Product 주소를 확인하며 중복 쿠폰이나 동일 쿠폰의 금액 충돌은 추측하지 않는다. 다른 행사만 있는 변형 4개에서는 화면의 현재 가격으로 복구했고, 양쪽 행사를 함께 둔 4개에서도 올바른 가격을 읽었다. 실제 쇼핑몰에서 이런 구조화 데이터 충돌이 관측된 것은 아니다.

**별도 신규 표본.** [손목시계 3개 첫 제출](https://github.com/user-attachments/assets/ae1e8a97-46f9-43df-971f-4c5df63bf9df)은 iOS 3/3, Android 2/3이었다. 지그재그 `110797193`(31,840원)와 에이블리 `4569918`(39,900원)는 양 OS에서 정확했고 Android의 로드된 사진 경로까지 원본 첫 사진과 대조했다. 무신사 `847457`(37,000원)는 iOS에서는 정확했지만 Android에서는 빈 수동 폼으로 끝났다. 이 시도의 HTTP 상태는 확인되지 않았다. 에이블리 Android 붙여넣기가 제출 **전** 멈춘 건은 제외하고 이후 처음 제출된 OS 공유를 셌다. 원본이 삭제된 지그재그 `143085551`·`150420447`, 원본 요청 실패 `119993859`는 제출하지 않았다. 앱 주소 변형 재시험은 신규 표본에 포함하지 않았다.

독립 웹은 쿼리를 포함한 에이블리 주소로 빈 수동 폼을 열었고 쇼핑몰 요청은 없었다. 자동 테스트 552개, 타입·코드 검사, 웹 빌드 통과. 실제 쇼핑몰과 로컬 Ziper API·시뮬레이터/에뮬레이터 기준이다. 운영 `/readyz`는 연결 리셋, 연결된 실기기는 없었다.

## 운영 API 도달 여부와 멈춘 세션 재발급에서 복구

**운영에서 확인한 범위.** 직전의 연결 리셋과 달리 이번에는 `api.ziper.cc`의 `/livez`와 `/readyz`가 `200 {"status":"UP"}`로 응답했다. iOS 시뮬레이터 Safari에서도 readiness 본문을 확인했다. 데스크톱 Chromium에서 실제 `https://app.ziper.cc`를 열고 쿠키/토큰 없이 규칙 조회, URL 확인, 보드 조회를 호출하자 브라우저가 `cors` 응답 `401 UNAUTHORIZED`를 읽었다. Android 에뮬레이터 Chrome에서도 같은 Origin의 readiness는 `200`, 규칙·보드는 `401`이었다. 운영 preflight는 `Authorization, If-None-Match`를 허용하고 `ETag`를 노출했다. 쿠키 재발급 preflight는 credentials를 허용했고 쿠키 없는 POST는 `401`이었다. **이는 인증된 규칙 `200 → 304`나 상품 등록 성공의 증거가 아니다.** 전용 운영 계정·실물 기기를 확인하지 못해 운영 저장과 수정은 하지 않았다.

**로컬 장애 실험.** 첫 규칙 조회가 `401`이어서 세션 재발급을 기다리는 동안, 로컬 서버가 재발급 응답 헤더와 본문 첫 글자만 보내고 멈추게 했다. 이때 규칙·URL 확인의 개별 대기는 끝나지만 재발급 자체가 계속 진행 중이어서, 다음 제출도 같은 미완료 요청을 기다렸다. Chromium에서 변경 전 두 번 모두 약 7초 후 실패했고 추출기는 한 번도 호출되지 않았다. 재발급 제한을 8초로 둔 중간 버전에서도 오류 직후 재시도하면 URL 확인만 성공하고 추출은 빠졌다. 최종 코드는 재발급 헤더부터 본문 완료까지 독립된 5초로 제한한다. 호출자 한 명의 취소가 다른 대기자를 중단시키지 않는다. 시간 초과를 로그아웃으로 확정하거나 재발급 POST를 스스로 반복하지 않는다. 브라우저에서 첫 시도는 약 5초 후 실패했지만 바로 다음 제출은 규칙을 다시 받아 추출기를 호출했다.

[Android·iOS의 오류와 같은 화면에서 재시도한 결과](https://github.com/user-attachments/assets/c3201ed4-979d-4e6d-9cb5-f42e76719839): 규칙 캐시가 없는 상태에서 에이블리 `9968973`을 제출하고 로컬 재발급 본문을 한 번 중단했다. `다시 시도`를 누르자 양 OS 모두 페이지를 다시 열지 않고 정규 URL·전체 이름·9,500원·데님 지갑 첫 사진을 채웠다. Android 재시도 후 정확한 폼까지 약 3.5초였다. 이 강제 장애의 첫 제출은 실패이며, 운영에서 이 장애가 관측된 것이 아니다.

**정상 규칙 신규 표본.** [세 쇼핑몰의 지갑 3개](https://github.com/user-attachments/assets/df2ea944-b33f-41da-916c-d5727273032b)는 로컬 Ziper API와 실제 쇼핑몰에서 최초 제출 iOS 3/3, Android 3/3 정확했다. 무신사 `110167`(32,000원, 품절), 에이블리 `9968973`(9,500원), 지그재그 `134445733`(16,780원)의 전체 이름·가격·첫 컷을 확인했다. 이 정상 표본은 재발급 한도를 조정하던 중에 측정했고 이후 같은 상품으로 한 장애 재시도는 더하지 않았다. 무신사 Android는 약 6.4초에 성공했지만 과거 403이 해소됐다는 뜻은 아니다. 독립 웹은 수동 폼만 열었고 쇼핑몰 요청은 없었다. 임시 계측 제거, 테스트 554개와 코드·타입 검사 및 웹 빌드 통과.

**[iOS에서 DNS 이름의 끝점이 있는 경우](https://github.com/user-attachments/assets/10cbaea2-c2d7-4d90-b0bc-a3ee74bc7205)**: 호스트 별칭을 인식한 뒤에도 `https://a-bly.com./app/goods/427026?coupon_sno=44081681`의 첫 iOS 제출은 1.757초에 빈 결과로 끝났다(Android는 정확). 같은 주소를 다시 계측해 보니 0.408초에 `a-bly.com.` 탐색, 2.250초에 `NSURLErrorDomain -1200`(보안 연결 실패)로 문서 없이 종료했다. 두 번째 요청에서 관측한 오류다. 최종 코드는 요청하기 전에 확인한 호스트명의 마지막 점 하나만 제거하고, HTTPS·앱 경로·쿠폰 쿼리는 유지한다. 인증서 검증이나 오류 처리·재시도 정책은 바꾸지 않았다. 깨끗한 번들로 원래 주소를 다시 제출해 양 OS에서 전체 이름·5,220원·첫 사진을 확인했다. 임시 계측 제거, 559개 테스트·코드 검사·타입 검사·웹 빌드 통과.

## 콜드 시작에서 유효한 쿠키 재발급이 2초를 넘는 경우

규칙 캐시가 없는 화면에서 첫 규칙 GET이 `401`이고, HttpOnly 쿠키 재발급이 **3.4초 뒤 정상 `200`**을 주도록 로컬 API를 설정했다. 수정 전에는 재발급 도중 규칙 조회의 2초가 끝나 추출을 건너뛰었다. URL 확인은 같은 재발급을 기다려 성공하므로 사용자는 오류 대신 빈 수동 폼을 받았다. Chromium에서 첫 제출은 약 3.41초 후 `ready`였지만 추출 호출 0회, 다음 제출은 추출 호출 1회였다. 수정 후에는 같은 첫 제출에서 약 3.42초 만에 추출 호출 1회와 URL 확인을 모두 수행했다(이 브라우저 실험에서 추출기는 호출 횟수만 측정). **운영 쿠키 재발급이 실제로 느렸다는 관측은 아니다.**

이제 쓸 수 있는 규칙이 없을 때만, `401` 뒤 별도 5초 한도가 있는 공유 재발급을 기다리는 동안 규칙 타이머를 한 번 멈춘다. 타이머를 새로 2초 주는 것이 아니라 **남은 시간만** 돌려준다. 회귀 테스트에서 첫 GET이 1.5초를 쓴 뒤 재발급이 3초 걸리면 다음 GET은 0.5초만 더 기다렸다. 유효한 캐시는 이전처럼 2초에 사용하고, 화면 취소는 다른 화면의 재발급을 취소하지 않는다. 재발급 응답 본문이 영영 끝나지 않는 별도 브라우저 실험은 5.005초에 첫 제출이 실패했고, 사용자가 다시 제출하기 전까지 재발급 POST나 URL 확인을 반복하지 않았다. 100ms 뒤 재제출은 추출과 URL 확인에 성공했다. 쇼핑몰 요청·타임아웃·거절 처리는 바꾸지 않았다.

## 이모지가 들어간 상품명 길이와 에이블리 문서 준비 시점

**상품명은 UTF-16 단위로 자르면 안 된다.** 운영 배포 커밋 `0277435`의 서버 JAR에서 검증 함수를 직접 실행했다. `가` 199개 뒤에 `🍑`가 붙은 이름(UTF-16 201단위)과 `🍑` 200개(400단위)는 그대로 허용됐고 201코드 포인트는 거절됐다. 기존 스캐너는 `slice(0, 200)`으로 끝 이모지를 반만 보내거나 이름 뒷부분을 잘랐다. 해당 경계를 재현한 테스트 4건은 수정 전에 모두 실패했다. 이제 브리지는 최대 400단위까지 제목 전체를 전달한다. 그보다 길면 이름만 수기로 남기며 앞부분을 완성된 이름으로 보내지 않는다. 폼에서는 200코드 포인트를 넘으면 원문을 보며 줄일 수 있지만 저장할 수 없다.

- **저장·수정 검증:** 로컬에서 위 JAR·격리 DB·테스트 계정으로 브라우저의 실제 수동 등록 폼을 사용했다. 201자는 저장 버튼이 비활성, 끝 글자를 지운 200자는 `POST 201` 후 상세 제목 끝의 `🍑`까지 일치했다. 편집에서도 이모지 201개는 비활성, 200개는 `PATCH 200` 후 새로고침·상세 GET에서 **400 UTF-16단위가 전부** 일치했다. 첫 사진을 긁거나 운영 DB에 쓰는 실험이 아니다. 제한에 걸린 실제 쇼핑몰 제목을 관측했다는 뜻도 아니다. 로컬 쇼핑몰 제목을 임시 변형한 별도 모바일 실험은 iOS에서 수동 폼·앱 열기 실패, Android에서 대기/스냅샷 실패로 경계값을 검증하지 못했다. 이 실험은 정확도 표본에서 제외했다. 코드 변경 후 자동 테스트 567개, 코드 검사, 세 앱 타입 검사 및 웹 빌드 통과.

**별도 정상 경로:** [신규 최초 제출](https://github.com/user-attachments/assets/54152290-ecec-40d2-b347-42b644a04009)은 무신사 `2177448` 29,250원, 지그재그 `113602661` 8,820원으로 두 OS 모두 2/2였다. 에이블리 `14012960`의 일반 숫자 쿠폰 주소는 기존 상품 대조로, 이번에는 iOS 3.41초·Android 9.69초에 정확했다. 이는 과거 같은 주소의 iOS 빈 폼 원인을 밝힌 결과가 아니다. 러너 빌드와 입력칸 탭에서 링크 제출 전에 멈춘 시도는 별도다. 단독 웹은 선행 0과 쿠폰이 있는 주소도 이름·가격을 수동 입력하게 했고 쇼핑몰 리소스 요청은 0건이었다. 권한·재시도·대기 시간은 변경하지 않았다.

에이블리 앱 주소 `/app/goods/014012960`도 별도 대조했다. Chrome과 양 OS의 최종 폼에서 `coupon_sno=45920189`가 있으면 10,140원, 없으면 10,900원이었다. 이름과 대표 컷은 같고 Android 두 경우 모두 같은 첫 이미지가 720px로 로드됐다. 배포 커밋의 서버 JAR를 로컬에서 실행해 정규화 함수도 확인했다. 서버 자체는 선행 0을 제거하지 않으므로 앱이 `/goods/14012960`을 URL 확인에 보내는 것과 사용자가 입력한 주소를 서버에 그대로 보내는 것은 다르다. 수동 웹이나 이미 저장된 카드의 중복까지 정리한 것은 아니다.

계측을 제거하고 수정한 뒤 [새 에이블리 두 상품의 최초 제출](https://github.com/user-attachments/assets/3a4a3e12-6eec-4032-9316-1fa04c9edc42)도 iOS·Android 각각 2/2 정확했다. `14888945` 16,160원과 `784442` 42,900원의 전체 제목과 첫 사진을 확인했다(Android는 Chrome 첫 슬라이드 URL과 일치, 각각 640/720px). 선행 0 주소는 이미 확인한 상품의 **다른 주소 대조**이지 신규 상품 성공 횟수가 아니다. 자동 테스트 568개, 코드 검사·세 앱 타입 검사·웹 빌드 통과. 운영 `/readyz`와 `/livez`는 이 환경의 연결 리셋으로 HTTP 응답을 확인하지 못했다.

## 리팩토링 전후 대조와 무신사 브랜드 접두 상품명

상품 링크·추출 코드를 `packages/product-extraction`으로 옮기고 쇼핑몰별 규칙을 `Shop` 전략으로 정리했다. 같은 링크 11개(에이블리 쿠폰·0이 붙은 앱 링크·단축 링크·일반, 무신사 일반·0이 붙은 링크·OneLink, 지그재그)를 리팩토링 전후에 iOS 시뮬레이터·Android 에뮬레이터로 최초 제출해 폼의 정규 주소·상품명·가격·이미지 로드를 비교했다. 실제 쇼핑몰, 로컬 Ziper API fixture 기준이다. iOS는 전후 모두 11/11로 같았다. Android는 리팩토링 전 측정에서 무신사 직접 링크 3건이 접근 거부로 실패했고, 리팩토링 후 측정에서는 거부가 재현되지 않아 열렸다.

열린 무신사 중 `/products/02177448`이 Android에서 `얼모스트블루(ALMOSTBLUE) 블러쉬 체크 머플러`로 채워졌다. 리팩토링 전 커밋(`a027de5`)에서도 2/2 같은 결과여서 기존 결함이다. 본문이 늦게 도착하는 동안 스캐너가 600ms 뒤 브랜드가 붙은 공유 카드 제목을 완성값으로 보냈고, 이후 도착한 상세 기록의 `goodsNm`은 반영되지 않았다. 이제 무신사 상품 페이지는 문서 파싱이 끝나기 전까지 카드 제목을 쓰지 않는다. 같은 흐름을 재현한 단위 테스트를 추가했고, 수정 후 Android 무신사 4개 링크 × 2회 8/8, iOS 4/4가 상세 상품명과 일치했다.

## 출시 전 남은 검증

[실제 자동 입력 재실행](../e2e/README.md#실제-쇼핑몰-자동-입력-재검증)으로 상품 링크별 자동 입력 결과를 확인할 수 있다. 이번 샘플 성공을 99%에 가까운 실제 성공률로 보지 않는다. 남은 무신사·에이블리 간헐 실패 원인과 더 많은 공유 링크, iOS·Android 실기기의 Wi-Fi·셀룰러, 운영 API로 규칙 조회 및 저장을 추가 확인해야 한다. 운영 readiness와 비인증 경로는 도달 가능했다. 다음 운영 검증에는 전용 테스트 계정으로 발급한 세션과 저장·수정할 테스트 보드가 필요하다. 유효 상품에서 전부 맞게 채운 시도만 성공으로 기록하고, 부분 입력·다른 상품 정보·쇼핑몰 거부·시간 초과는 성공에서 제외한다. 운영 출시 판단에는 쇼핑몰·링크 형태·OS·네트워크별로 분산된 표본을 사용한다. 참고로 독립·대표 표본에서 실패가 0건이어도 99% 성공률의 단측 95% 하한을 주장하려면 최소 299회가 필요하다. 같은 링크를 같은 환경에서 반복한 횟수는 그 표본을 대신하지 않는다.
